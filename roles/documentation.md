# Documentation

Own reader-facing guidance and examples across Core and Daymark. Load [shared guidance](shared.md).

- Name the reader and the question before editing. Reuse or consolidate an existing page; add one only for a distinct task that has no home.
- For people, explain the purpose with a concrete example before code or terminology. Define a term when it first becomes necessary. Keep domain examples separate from what Keir itself provides.
- For agents, specify required inputs, ordered actions, tools and boundaries. Link the matching authoring guide and canonical contract instead of copying their rules.
- Give each contract one authoritative home. Put commands in runnable guides, compatibility/pins in their catalogs, and dated qualification/design evidence in existing contributor records. Keep version numbers only where they change a reader's action.
- Check the whole newcomer path with an unbriefed reader, verify links/commands and get technical review of contract changes. Fix confusion; do not compensate with another page or disclaimer.
- Preserve frozen guides, archives and required history. Label proposals and historical snapshots; do not present them as current instructions.
