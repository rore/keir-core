# Keir hooks, result consumers, and tenant capabilities

**Architecture v0.4 | 28 October 2026 | host-integration design draft.** This document expands the Domain Capability Model (DCM) and compilation context, **not the v0 IR step language**. Proposals here are not implemented or certified. The initial `TaskCompleted` task-domain fixture is unchanged.

## 1. Principle and ownership

Keir is an **agent-independent controlled extension language, compiler and runner**. Its authoring source can be handwritten or generated by any host-integrated agent. It enforces declared authority and bounded operations; it cannot determine whether a business policy is correct or an approved endpoint is trustworthy. A trusted host adapter is still necessary.

The **host** chooses where extensions run, which tenant/customer is involved, which operations may be called, and how a typed result changes the native business flow. The framework never invents an extension hook or changes the surrounding application control flow by itself.

## 2. Entry point and result consumer

Four proposed invocation phases:

| Phase | Host invocation | Permitted result | Host obligation |
|---|---|---|---|
| `PRE_OPERATION` | Before a native operation proceeds | `ALLOW`, declared `REJECT`, optionally constrained `PATCH` | Enforce bypass prevention, validate final input again, apply host-defined error/timeout policy |
| `POST_COMMIT` | After an operation is confirmed committed | Typed result or permitted follow-on effect | Cannot retroactively reject original commit; host controls delivery/replay |
| `RESPONSE_TRANSFORM` | Before returning a bounded response | Approved filter/selection/order or projection | Protect immutable fields, ensure source completeness, preserve existing native semantics |
| `ON_DEMAND` | A user or host asks for a decision or view | Typed result | Caller decides where to use result; no implied persistent workflow |

A DCM entrypoint contract MUST specify its type, its authoritative input projection, allowed capabilities/effects, allowed **result variants**, maximum calls/output sizes and a host-managed total execution deadline. For pre-operation hooks it MUST additionally state placement relative to native checks and commit, and the host's behavior on invalid results, timeout, transient failure or uncertain side effect. The **host**, not the extension program, selects fail-open/fail-closed or other fallback semantics. Policy decisions must not silently bypass security-sensitive native validation.

A `PRE_OPERATION` hook can reject only before the host commit, never undo a concurrent or completed effect. If an external service is called, avoid holding a database transaction across the network call. The host must revalidate mutable business facts before committing. A returned patch is data, not direct authority to mutate protected fields.

### Illustrative future hook contract (not in current DCM fixture)

```yaml
id: BeforeTaskCreate
phase: PRE_OPERATION
input: ProposedTaskCreate
output: TaskCreateDecision
allowedResults: [ALLOW, REJECT]
consumer: task-service.create-validation
failurePolicy: FAIL_CLOSED  # chosen by host configuration, never by IR
deadlineMs: 600
capabilityGrants:
  projects.get: 1
allowedEffects: [project.read]
```

`ProposedTaskCreate` and `TaskCreateDecision` must be defined as closed typed records in an approved DCM revision. The host adapter for `projects.get` supplies scoped project data. One possible policy is: reject an urgent task in a project marked `requiresJustification` when no adequate notes are present. The output `REJECT` only works if the host *actually blocks* creation. This illustrative YAML is a **contract sketch**, not a validated Keir IR or a finalized DCM schema.

The matching Keir extension would use the **ordinary v0 instructions**, without a new ``HOOK`` task or specialized workflow instruction:

```yaml
# Illustrative step fragment only, not a complete validated definition.
steps:
  - id: project
    call: projects.get
    args:
      projectId: {cel: 'input.projectId'}
  - id: reject
    let: {cel: 'project.requiresJustification && input.priority == "URGENT" && size(input.notes) < 10'}
return:
  record:
    decision: {cel: 'reject ? "REJECT" : "ALLOW"'}
```

A complete program must pin the new DCM revision and declare presence handling for optional ``notes`` before it can pass static checking. The entrypoint declares which decision enum values are valid. The **host** consumes the result; Keir does not call task creation itself for an ``ALLOW`` decision.

## 3. Effective capability catalog per tenant

The **shared DCM** is issued by the SaaS owner. A **tenant capability registry**, when supported by the host, contains extra admitted operations (for example, tenant-specific decision or data providers). A trusted compilation request resolves:

```text
Shared domain DCM  +  host-approved tenant capability registry
                    |
                    v
       Effective capability catalog, version and digest
                    |
                    v
   Keir IR + trusted tenant/entrypoint context -> compiler
                    |
                    v
       Tenant-bound, approved portable compiled artifact
```

Capability names are statically known and explicitly namespaced (such as `tenant.verifyCustomer`). Tenant capabilities must not shadow or replace shared capabilities, hook contracts or host-only parameters. The compiler checks both kinds uniformly: typed agent input, host-bound input, result/error types, effects, grants, preconditions, work limits and approved protocol timeout. The artifact must pin the **shared DCM digest**, **effective catalog digest**, **tenant activation scope** and **hook consumer contract version**. The current IR's `domain.fingerprint` remains the shared DCM fingerprint; trusted compile context supplies tenant resolution without adding a user-authorized tenant field to the IR.

An endpoint may be changed behind an existing capability only if the host certifies unchanged semantics, grant/scope and contracts. Otherwise recompile and reapprove. In production, the runner verifies that the currently authorized host/tenant has the same compatible admitted capability set and registered adapters. This protects against cross-tenant name collisions.

## 4. External endpoints are host adapters, not new IR instructions

**The host owns:** registering/verifying an endpoint and its owner; destination/SSRF/egress and tenant policies; secrets/authentication; data disclosure rules; actual HTTP/gRPC transport and network timeouts; concurrency, idempotency and error evidence; endpoint removal and version migrations.

**Keir owns:** resolving statically named admitted calls; type-checking CEL/arguments/returns; enforcing declared effects and total/per-call resource budgets; passing protected parameters only to host adapters; interpreting typed success, business rejection, transient failure or `UNKNOWN_COMMIT`; tracing and simulation. Keir must not make an arbitrary network request from an IR `url` or treat endpoint registration as part of program execution.

Host-approved per-call timeout cannot exceed the remaining invocation deadline. A network timeout for an effectful operation may mean `UNKNOWN_COMMIT`, not definitely no effect; the host adapter defines this classification. No automatic retry in v0. As a first integration profile, favor **read-only or decision-producing customer endpoints**, not remote mutations requiring distributed recovery.

## 5. Optional AI authoring integration

Keir exposes compiler, DCM discovery and simulation APIs; its core has no LLM dependencies. A host may offer a conversational assistant that interprets requirements, proposes scenarios, generates IR and revises it from compiler diagnostics. Agents cannot self-certify host guarantees or approve their own changes. The host may optionally expose **endpoint registration proposals** as a separate tool, subject to host control. Without that tool, the agent must only use already admitted capabilities.

An optional Keir skill or MCP/CLI wrapper may explain how to use those APIs. The **host's** UX and agent implementation are intentionally out of Keir's runtime scope.

## 6. Tests and rollout boundary

Future hook/tenant integration tests should verify: pre-operation `ALLOW` and enforced `REJECT`; missing/invalid decision; legal/forbidden patch; transient timeout and host fallback; total deadline accounting; native validation cannot be bypassed; effective catalog digest and tenant scope are checked; unregistered endpoint is rejected; registered endpoint uses only trusted adapter/credentials; no arbitrary URL/exfiltration appears in IR; post-commit failures cannot undo committed operations. Simulation covers declared fake adapter outcomes; actual network trust, isolation, availability and database commit boundaries require separate host tests.

**First POC remains unchanged:** `TaskCompleted`, native reads and one host-managed write, CEL-Java compiler and Node runner with the same approved artifact for simulation/production. `BeforeTaskCreate` and tenant endpoints are **subsequent capabilities**, not initial blockers. The compiler and runner must be designed to support their future typed contracts without adding general workflow orchestration.
