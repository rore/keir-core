# Generic hook contract correction

Status: reviewed implementation target for [generic-hook-capability-contract](../../../roadmap/features/generic-hook-capability-contract.md). This record accompanies the [revised contract](../../specs/generic-hook-capability-contract.md); it is not implementation evidence. The existing read/effect checkpoints keep their current contracts.

## Decision and rationale

The first profiles made a hook, admission and invocation each enumerate capability counts. That makes a sample program's call list a prerequisite for authoring. It reverses the intended division: the host publishes a safe catalog and generic hook; the customer composes behavior the host did not prewire. Removing only example grants would fail schema validation and leave compiler/runtime enforcement unchanged.

The correction separates five concerns: catalog visibility, typed hook/lifecycle/consumer, source composition, static admission/resource constraints, and current native authorization. No required per-capability configuration remains in the proposed defaults. Optional allow/deny/quota controls are restrictions only. Aggregate budgets already bound repeated reads; named quotas must not masquerade as the only resource control. A fixed published catalog can serve different programs without a hook change, while a changed catalog still requires repinning and recompilation.

Use new `keir-read/2` and `keir-effect/2` profiles rather than changing the meaning of missing fields in old artifacts. Keep the source family, instruction grammar, adapter signatures and consumer results unchanged. The authored-constant correction below adds explicit nominal literal typing without a configuration channel. The effect ceiling remains at most one; read hooks can share a catalog containing write definitions but cannot call them. Optional controls inherit and narrow upstream restrictions; they never create authority.

## Authored constants and fixed hook payload

The customer-selected eligible project and fixed title belong inside the authored program. Preserve the host-defined hook payload, including legitimate fields unrelated to this example. The earlier configuration recommendation is superseded: no configuration declaration, compiler-supplied settings record, new CEL namespace, storage or binding framework is required or authorized. Values from another source must be obtained through explicit program logic.

The current fixture's `given.input.projectId/title` proves only injected test data. Inspection of `Expressions.literal`/`assign` and `KeirCompiler.binding` shows the actual gap: a plain string cannot construct a nominal ProjectId, and source bindings have no typed-literal form. The [proposed minimal correction](../../specs/generic-hook-capability-contract.md#event-facts-extension-choices-and-protected-authority) adds `{literal: string, type: declaredNominal}` to `/2` bindings, reusing BIND, existing typed artifact literals and nominal provenance. A fixed title already works as a String literal. Typed business IDs are not authority or native idempotency keys.

Later implementation surfaces: compiler `Expressions.java` and `KeirCompiler.java` binding shape/preflight/lowering; Java `Artifact.java` and Node `validation.js` literal compatibility; checked-expression provenance and shared fixtures. Retain `/1` rejection and bytes. Tests cover wrong nominal types, dynamic-cast rejection, unknown/non-nominal annotations, bounds, protected overrides, source/artifact revision changes, and current resource authorization. No new host input or configuration API is needed. The nominal-literal spelling/diagnostic contract awaits review; authored constants are the corrected product invariant, not a choice between configuration models.

No policy engine, endpoint registry, overlay language, durable workflow, new key machinery or production activation system is needed. New profile acceptance remains separate from production qualification.

## Reconciliation with historical proposals

The [hook baseline](../design-baseline/public/host-integration-and-hook-contracts-v0.5.md) correctly separates definition, invocation and consumption, and keeps protected context outside source. Its required `capabilityGrants` framing and program-specific examples are superseded for the corrected default. The [tenant/catalog baseline](../design-baseline/public/hooks-and-tenant-capabilities.md) remains useful for host-approved discovery and endpoint publication boundaries; this revision does not implement endpoint registration or expand customer authority.

The [v0.7 proposal](../design-baseline/public/host-owned-idempotency-and-multi-effect-contracts-v0.7.md) is a **future direction**, not an enabled execution mode. Preserve its original host-owned, typed key pass-through and native idempotent adapter requirement. Keir must not derive a step key, stringify an opaque value or substitute an execution/event ID. Distinct labels, API routes or static step IDs do not prove independent deduplication scopes. A provider accepting a key header does not establish atomic duplicate suppression, payload matching, concurrency behavior, retention or result recovery.

Two duplicate-safe writes are still two independent commits. If A confirms and B rejects, A remains committed; if B times out, retain A=CONFIRMED and B=UNKNOWN. Neither failure permits an ordinary all-or-nothing success or a claim of rollback. A future contract must define sequence-level classification and per-call receipts, stop behavior, host reconciliation, and whether a durable journal/result recovery exists before offering retries. Compensation is another fallible effect, not implicit rollback. All-or-nothing behavior belongs in one host-owned atomic domain capability when that is the actual requirement.

Before any future multi-write profile, require verified native key type/value preservation, payload-match and concurrent duplicate behavior, key retention, recoverable results/status, certified collision boundaries across operations/events/active bindings/native callers, pinned activation on redelivery, and fresh authorization. Reuse the original host key only where the adapter contract proves same-key recovery safe; changed arguments or expired retention require rejection/reconciliation. Do not infer safe replay merely from duplicate suppression. The current correction adds neither v0.7's sequence mode nor key slots, retries, collision metadata or partial-sequence classification. Its one-write ceiling is mandatory even if a host claims idempotency.

Generic defaults require a separate host-approved widening decision; automated field deletion is not migration.

## Review gates

The [complete ownership walkthrough](../../specs/generic-hook-example.md) supplies a proposed full DCM/source and compile/prepare/invoke boundaries. Its DCM fingerprint is computed from the displayed model; no `/2` compiler output or execution is claimed. Review this coherent final ownership model before implementation: fixed host payload, customer-authored constants/composition, compiler validation/artifact, runtime enforcement, and separate host/customer assistant authority. The earlier configuration proposal is superseded, not an unresolved product option. Literal spelling and implementation diagnostics remain technical review gates.

Design review accepts the ownership model, `/2` compatibility boundaries, optional-control semantics and explicit nominal-literal form as the next implementation target. These choices are not executable support: compiler, both runtimes and shared conformance must qualify them before use. Java SDK type/overload names and corpus directory names are implementation choices subject to those semantics, not reasons to change policy. Real adapter admission, broader hook lifecycles and v0.7 recovery remain separate work. Do not defer the generic default behind those features.
