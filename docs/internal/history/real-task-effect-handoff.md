# Legacy `/3` real-task effect handoff

> This handoff records host-specific native persistence and preservation evidence. It is not a generic runtime initialization credential or a prerequisite input to corrected `/4` bind/prepare calls. The host remains responsible for its actual permission, key and commit guarantees. The demo's new definition identity and migration/activation behavior belong to its owner; this handoff does not change them.

**Legacy `/3` plan status:** proposed implementation contract; not implemented or accepted. This described the first task-effect integration under the old qualification protocol. It is preserved as host-specific planning and evidence; it is not a generic `/4` initialization contract. Core stays domain-independent. The demo owner controls any new task definition identity, migration and activation behavior.

## Customer contract and catalog

“When I complete a task in this existing project, create a task with this title in the same project.” Resolve the project's exact owner-scoped ID from native project choices; compile project/title as customer-owned constants. Ask when a name is ambiguous. The host does not put customer choices into event fields or implement a special follow-up adapter.

Publish one TaskCompleted EVENT/AFTER_COMMIT hook with input `{taskId}` and protected event `{id, source}` using the existing effect event contract. Source and input identify the same task. Generic `tasks.get(taskId)` returns `{id, projectId, status}`; `tasks.create(projectId, title)` returns `{id}`. Both bind actorId from trusted owner context. Status enum is OPEN/COMPLETED; IDs are existing nominal strings. Create uses existing title constraints and empty native notes; no due date, parent link, tags, search, scheduling or hidden business uniqueness. The program reads, compares completed status/project, and conditionally creates once. Hook result is a small `{status: CREATED|NO_OP}` report, whose text cannot override native evidence.

Use a new exact demo model version with effect/3, a new EVENT_REPORT consumer identity and new pins. Retain old read models by identity. Compiler profile, admission, simulation, proof validation and execution route through the item's pinned host definition instead of global ClassifyTask/read assumptions. No browser or model argument selects arbitrary executable adapters.

## Durable records

Add two native tables in one transactional schema migration; names are illustrative but keys and fields are required:

* `task_completion_events`: event_id primary key, unique task_id (the native app has no reopen), owner_id, original_key unique, source_task_id, immutable input JSON, nullable selected item/revision and exact artifact/model/compiler/environment/consumer/binding-evidence pins, state, runtime outcome, reconciliation JSON. Foreign keys preserve owner scope. State is NO_BINDING, PENDING, STARTED or FINISHED. The immutable event/key/selection columns never change after insertion.
* `task_effect_receipts`: owner_id, capability_id, original_key as composite primary key; canonical validated payload bytes; terminal native result JSON and effect classification; optional created_task_id. Native transaction commits receipt and created task together. Keep records without TTL for this increment. Deletion retains both tables and pinned dependencies.

The current demo is schema 7; this additive migration is schema 8. Add `UNIQUE(tasks.id, tasks.owner_id)` before using composite owner/task foreign keys. Preserve existing native and authoring rows without a table rebuild. Include both new tables in backup byte verification, reset dependency ordering and old-version test fixtures. No events are backfilled for already-completed legacy tasks.

Scope the first key contract as `demo.TaskCompletionKey/1`: the native completion service allocates a UUID once and persists it as original_key. The Node host rehydrates an immutable branded key accepted by its validator; Java qualification fixtures use the corresponding immutable UUID value. Runtime never reconstructs it. Adapter accesses the key through the host-native representation, not generic conversion hooks. The database uniqueness namespace is owner + capability + original native key. No per-step or artifact-derived keys. Event ID is distinct audit identity; never derive the operation key from it.

Payload identity is the canonical validated `{projectId,title}` plus the protected owner and capability/version contract. Resolve native title normalization once before hashing/comparison and document it identically for initial and repeated calls. Store exact canonical bytes as well as any index digest; digest equality alone is not the mismatch check. Exact-key/different-payload calls reject with declared `KEY_PAYLOAD_MISMATCH`, NONE for that attempted dispatch; they do not deny that an earlier different request may already have committed.

Native task-service API adds an internal keyed creation entry point using the same validation/access rules as ordinary create. It accepts trusted actor, native key and business arguments separately. Browser CRUD does not gain authority to supply this internal key or event context. Atomic duplicate lookup/insert/task creation runs in one SQLite transaction. Matching successful receipt returns its saved task ID even if the task has subsequently changed; recheck current authority before disclosing it. A definite rejection may be retained as NONE; unknown outcomes never become synthetic success or NONE. Receipt writes and native tasks are not authoring spend records.

The concrete internal call is `createTaskOnce(owner, nativeKey, {projectId, title})`. Resolve nativeKey to an existing completion event owned by owner; an arbitrary or cross-owner key is rejected before receipt disclosure or creation. A matching stored receipt can be read after the event is FINISHED. A missing receipt permits a new creation only in STARTED state with the matching qualified binding and current write authority. Reject non-string or ill-formed Unicode projectId/title at this internal boundary before normalization, canonical encoding, receipt comparison or mutation; then apply existing native project lookup, title trim and title-length validation. Do not normalize project IDs. Retain the existing 120 UTF-16-code-unit title bound; optional notes are not part of this first extension capability. Compare canonical `{projectId,title}` bytes and capability version for an existing owner/capability/key receipt. A matching successful or durable business-rejection receipt returns the original saved result without another mutation. Persist declared deterministic native business rejections as NONE; do not persist an access-denial response under another owner's key, transient availability failure as a permanent business rejection, or an uncertain result as NONE. UNKNOWN belongs to the reaction record unless an authoritative native receipt exists; no fake terminal native receipt is inserted to fill the gap.

Expose a separate owner-scoped read-only receipt/status lookup by event identity. Program disable, deletion or qualification revocation denies new execution but does not erase the owner's right to inspect retained audit under current read authorization. That lookup never calls an adapter, creates a task or grants write permission; redact inaccessible task/project details. Keep immutable native result identity separate from a fresh task DTO, which may have changed. Returning a saved identity is not proof that the task's current title/status still equals its creation result.

## Completion and selection boundary

In the existing completion service's native transaction, update only open -> completed and insert its event. Repeated completion of an already-completed task returns native state and creates no event/key. Snapshot the current owner's TaskCompleted selection and exact pins once in that transaction; no binding records NO_BINDING. The task completion and this bounded persistence succeed or roll back together. No runtime/compiler/provider or external I/O is called under the transaction. Invalid selected dependencies are captured as a later reaction failure; they do not undo valid native completion.

The existing synchronous `BEGIN IMMEDIATE` helper is non-nestable. Make native completion the transaction owner and use transaction-internal helpers for its row update/event insert; keyed creation likewise owns one transaction with raw validated task insertion, rather than nesting public transactional methods. The native HTTP completion response remains the existing task DTO. The event snapshot retains item/revision IDs, selection generation, artifact digest, complete modelRef, compiler/environment, exact consumer, qualification ID/revision/report digest and hostBuild. Copy stored pins under the transaction; validate/load executable dependencies afterward. A failed reaction never replaces a successful native response with a request to complete again.

After commit, dispatch PENDING work in the same process using a bounded local runner. Use an atomic PENDING -> STARTED claim before invoking the runtime. Concurrent duplicate deliveries see the existing state and never invoke a second run. FINISHED returns its saved result; STARTED remains in progress/uncertain and is not dispatched again. Do not create a durable workflow engine or an automatic retry queue.

On startup, PENDING means no invocation claim occurred and may receive its first dispatch. STARTED without a finished outcome is interrupted/uncertain: do not invoke again. Read-only receipt reconciliation may establish a native committed task, but cannot reconstruct the runtime's full outcome or rerun a possibly executed program. No receipt alone is not proof of no effect until the local transaction state has been recovered and the host has authoritative knowledge; do not automatically retry even then in this increment. FINISHED and NO_BINDING never execute on startup. A crash before STARTED commit leaves PENDING; a crash after it intentionally favors non-duplication over guaranteed reaction delivery.

Native completion returns success independently of reaction outcome after native commit. UI can refresh the separately recorded reaction result; no provider work is part of normal task completion. A failed/uncertain reaction never uncompletes the source task.

Retention horizon is the lifetime of this native dataset, not a timeout. Existing explicit stopped-app reset remains a destructive dataset boundary: first verify a recoverable backup containing native tasks, both event/receipt tables and prior accounting, then clear native events and receipts together in foreign-key order. Never clear receipts while retaining replayable events, nor import archived events alone. Old keys missing from the current event table are rejected by the internal API. A restored dataset restores its event/receipt/task state together; STARTED remains non-replayable. No ordinary customization deletion, release or migration resets this horizon or authoring held spend.

## Authority, lifetime and concurrency

Persist event ownership independently of browser login. Dispatch selects the recorded program for that owner, not the current browser user or newest active selection. Validate source/input equality, owner-visible source/project, current binding qualification and current user/resource access before dispatch and again in the native create transaction.

Selection replacement affects future completion admissions. An already admitted old revision may finish while its exact dependency and approval remain valid; retain that package/model/binding. Explicit disable, deletion, approval revocation or qualification revocation denies not-yet-dispatched effects, including pending old admissions; preserve an auditable failed reaction. Distinguish replacement from revocation in host authorization rather than using current-selection equality as the sole permission check. Already committed effects remain committed. No cross-user access arises from matching project IDs.

The source task's project cannot currently move and completion cannot reopen; tasks.get reads current native fields under this first contract. Repeated completion of that same already-completed task is a duplicate native request, not a new occurrence. Reopen/re-complete is unsupported; adding it requires a revised occurrence identity and removal of the per-task uniqueness assumption, not reuse of the old event/key. No global ordering across different task events is promised.

Creation itself emits no TaskCompleted event and cannot immediately recurse. However, a person later completing the generated task in the chosen project creates a new legitimate completion occurrence and matches this rule again. Its new source task receives its own native event/key. Do not silently exclude generated tasks, add an origin filter inside the adapter, or promise one task ever per project. Explain this behavior in the business scope and include it in checked examples. A customer-requested exclusion needs an explicitly supported source-authored condition and published data; it is not implicit host policy. Future automatic hook chaining requires a separate causation policy.

Stop/delete authoring remains governed by the existing settled-work gate. Deleting a customization prevents new event admissions and revokes undispatched effects for that item; it retains runtime receipts, original keys, source task and created tasks. Never cascade-delete real task effects with a customization. An invocation may already have dispatched when deletion occurs; report its honest outcome.

## Approval, Studio and legacy retirement

Use one active binding per owner and hook. Migrate existing owner-only selections to their original ClassifyTask hook without changing identity or generation. TaskCompleted starts with no selection. Existing read approval never authorizes a WRITE; no implicit substitute program or cross-hook rollback. Pin the exact new artifact and independently checked scenario suite; explicit human approval and turn-on are still required.

Activation creates no task and does not scan or replay old completions. Its effective boundary is the serialization order of the activation transaction and the native completion/event transaction: a completion committed before activation keeps its original selection or NO_BINDING; one admitted afterward captures the new selection. The same rule resolves concurrent replacement/completion. Native title validation currently trims outer whitespace; show the exact resulting stored title in the reviewed expectation, and clarify if that differs from the customer's intended title rather than promising byte preservation the service does not provide. New tasks start open with empty notes and ordinary native timestamps.

New customization discovery offers the qualified task hook, native project choices and accurate generic operations. Keep authoring tools limited to discovery, clarification, compile, examples, simulation and review offers. No agent approval, activation, event injection or real task-write tool. The assistant explains the trigger, chosen project/title, example differences and observed effects; it does not expose source/compiler terminology as the normal workflow.

Retire the advice action and default advice examples from the normal task/customer creation experience in the reviewed rollout. Preserve old item names, bytes, evidence, discussions, selections, tombstones and all financial/UNKNOWN records; expose them as clearly labeled legacy read-only records. Legacy selection remains historical metadata and is not used by the new completion dispatcher. Remove old advice execution/activation routes from customer use with an explicit retired response; do not silently point them at the new hook. Read-only export/inspection remains available. This is an intentional product retirement requiring acceptance of this plan, not a generic runtime compatibility break. Normal task CRUD remains usable with no extension.

Old pending authoring/creation receipts resolve to retained legacy work and cannot start a new real-effect conversation or silently resend. Preserve their original operation identities and settled/UNKNOWN accounting. A new task customization starts from an explicit new customer request and receives fresh review; copying old discussion text is not approval. Settle running old authoring before rollout using the existing Stop boundary, without resetting held spend.

The contextual canvas shows proposed examples and, separately, recent real reaction receipts. Show a link to a created native task only with authoritative CONFIRMED evidence; explain a no-match result as no task created, rejection as rejection, and UNKNOWN as “The task may have been created; we could not confirm it.” A source-authored CREATED label alone grants neither success nor a link. Read-only reconciliation is visibly separate from the original runtime result. Generic chat/canvas/continuity fixes remain reusable; no extra advice-only persona round establishes acceptance.

## Implementation seams and acceptance

Core changes: profile/format selection and DCM validation in compiler; artifact/binding/admission checks in both runtimes; current qualification checks; /3 scenario/consumer fixtures and packaged examples. Keep existing /1-/2 tests and semantics. The core [shared acceptance list](https://github.com/rore/keir-core/blob/3eefc59183c93efe0bce6bb56e7100a43fa06bc1/docs/specs/real-single-effect-admission.md#required-shared-acceptance) is mandatory.

Demo changes: native completion and keyed creation in task service/data migration; small event dispatcher and invoker binding; exact pinned model catalog/compiler selection; effect simulation and proof validation in lifecycle; per-hook selections; scoped project discovery and business summaries in authoring; retirement/direct-link handling and task outcome UI. Preserve deletion, replay identities, human approval boundaries and existing authoring accounting.

Required native checks use isolated SQLite databases and controlled barriers, without paid providers:

1. Atomic first completion/event, repeated completion, no binding, matching/nonmatching projects and two different authored titles/projects without new adapters. Completing the generated task later is a distinct event and can create another task; editing its title alone emits no completion. Reopen attempts remain unsupported. Activation alone and previously completed tasks create nothing; transaction-order tests resolve activation/completion races.
2. Concurrent event claims and same-key creates, mismatch with no extra task, owner isolation and unchanged native validation.
3. Crash at event commit, claim, create transaction and outcome persistence; native response loss, UNKNOWN, read-only reconciliation and no hidden replay.
4. Queue user A's event, switch browser to B, dispatch A with A's pinned program and fresh authority. Revoke source/project access and qualification; no unauthorized write.
5. Replacement versus disable/delete/revoke, old dependency retention, missing package/model, deadlines before/after dispatch and definite native evidence retained after output failure.
6. Schema upgrade/reopen and byte-preserved legacy records, authoring holds/UNKNOWN, native tasks and old receipts. New hook has no migrated approval or selection. Rollback is restore of an isolated backup plus matched old application, never downgrading a written live database in place.
7. Ill-formed Unicode project/title arguments reject before canonicalization with no task/receipt change. Valid supplementary characters remain intact and native title trimming produces the same canonical identity on repeat calls. This keyed-boundary check does not silently change ordinary browser CRUD.

Browser acceptance: describe the rule with an existing project and customer title; review synthetic matching/nonmatching/failure examples; approve and enable exact bytes; complete a real task and observe the actual new task; complete in another project and observe no creation; disable and observe no new admissions. Confirm native completion remains successful on a reaction failure, repeated submission creates no duplicate, legacy records remain accessible and no advice concept drives the main workflow. Qualify the SQLite report/build, then separately review rollout and preservation evidence. No second host or real remote transport is needed.
