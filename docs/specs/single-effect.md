# Single-effect profile

This page owns the common single-write source/dataflow, lowered CALL, effect outcome, trace and EVENT_REPORT semantics. They apply to effect/1, effect/2, effect/3 and effect/4 unless a section explicitly names a version. [Host model binding](host-model-binding.md#effect4-binding-and-preparation) owns the effect/4 API; [runtime execution](runtime.md#effect4-execution) owns invocation and limits; [host evidence and key identity](real-single-effect-admission.md#effect-outcomes-and-key-identity) defines the host's obligations. Implementation status and conformance evidence belong in [testing](../testing.md).

## Effect/4 and legacy boundaries

| Contract | Effect/4 | Earlier profiles |
| --- | --- | --- |
| Identities | `keir-effect/4`, `keir-dcm/effect-4`, `keir-artifact/effect-4`, `keir-scenario/effect-4` | Exact `/1`, `/2` and `/3` identities retain their behavior |
| Model assurance and mode | `HOST_BOUND_SINGLE_WRITE`; homogeneous real or simulation implementations | Effect/1–2 require `SIMULATION_ONLY`; effect/3 real mode requires its qualification protocol |
| Model/artifact structure | Reference model; optional DCM `capabilityPolicy` and `effectGrant` (default one) | `/1` embeds model/descriptors and requires grants/effectGrant; `/2`–`/3` use reference models and optional policies |
| Source | Guards, terminal handlers, explicit nominal literals; bounded String concatenation | `/1` lacks nominal annotations; `/2`–`/3` have them; all earlier profiles reject concatenation |
| Host context | Fresh bindings, deadline, original non-null key and typed event; implementations check permission/key authenticity | Legacy APIs retain authorizer, grants or narrowing policy, keyBinding and scope/qualification as versioned |
| Effects and consumption | At most one potential WRITE; NONE/CONFIRMED/UNKNOWN and EVENT_REPORT | Same common evidence and consumer rules |

No profile may turn a guarded second WRITE into an admitted program. A skipped write has no effect receipt. Neither a successful simulation nor a program-authored result proves a native commit. A handled business rejection may carry both a validated result and its original error, as specified below.

## Versions and inherited rules

This section preserves the effect/1 identity and embedded-model rules. Effect/4 uses the version boundaries above and the [reference artifact contract](compiler-artifact.md#effect4-identity).

Select `keir-effect/1` in the trusted compiler environment; retain source family `keir/v0`. Require DCM format `keir-dcm/effect-1` and artifact format `keir-artifact/effect-1`. These identifiers are profile compatibility boundaries, not release versions. Use the exact supported compiler build identity selected by the host; do not relax existing compiler/environment pins. CEL/protobuf package pins, scalar types, operators, descriptor recipe, canonical encoding and external artifact/DCM digests are unchanged. Reject mixed profile/format pairs; never infer a profile from source constructs or upgrade an old artifact.

The [read contracts](README.md) apply except for the explicit additions below. No collections, optional values, numeric business values, time, retries, recovery, multi-effect namespace or general branch language is added. All [existing ceilings](runtime.md#limits) remain: raw source and raw DCM each <=65,536 bytes, canonical embedded DCM <=65,536 bytes, artifact <=1,048,576 bytes, eight steps, four potential calls, 512 total AST nodes and 64 trace events. Canonical DCM overflow fails compilation with `BUDGET_EXCEEDED` at `/dcm`, preparation at `/artifact/dcm`; no artifact/prepared handle. Add a ceiling of **one potential WRITE call**, counting guarded calls even with constant-false guards. No mutual-exclusivity analysis. All handler expressions count toward aggregate AST/byte limits.

## Source and definite availability

All effect versions use the `keir/v0` root and the common binding representation. Explicit nominal source annotations apply from `/2` onward; effect/4 additionally permits the [String concatenation pair](language.md#types-and-cel-bridge). BIND remains `{id,let}`. CALL is `{id,call,args,when?,onError?}`; no other fields. Optional fields must be absent or valid, never null. `when` is a step identifier naming an earlier unconditional Boolean BIND, not an inline expression or a call result. All BINDs are unconditional. `onError` is a nonempty map of at most 16 declared capability business codes to `{record:{field:binding,...}}`; each record must match the entrypoint output exactly. No handler calls, retries, nested handlers, error variable or dynamic error selector.

An expression's environment contains `input`, earlier BINDs and earlier **unguarded** CALL results. A guarded CALL result is excluded from every later expression and handler environment, even under the same guard or a CEL conditional. Reject references with `DATAFLOW_UNAVAILABLE`; no `has`, optional, null placeholder or path proof is introduced. A guarded successful result is still fully validated before continuing. It need not be placed in CEL state. An unguarded CALL result is available on the continuing success path only. A handler sees the environment immediately **before its own call**, never that call's result or later bindings.

False `when` skips argument evaluation, any legacy per-call authorization callback, dispatch and handler evaluation; it consumes a reached step but no dynamic call/effect count. Invocation input, key, event and protected-binding validation still precede all steps. A true guard follows normal checks. No handler can catch a runtime authority, validation, resource, transient or uncertain failure. A host implementation's declared BUSINESS_REJECTION follows the ordinary terminal-handler rules, including when its business code denotes denied access. A declared BUSINESS_REJECTION terminates: evaluate the matching handler if present, then stop; otherwise return no result. Never execute later steps or the root return after a business rejection.

Whole-document parse/shape, DCM compatibility (and external pins for legacy APIs), and structural/authority/reference preflight precede expression checking. Preflight includes guard references, handler code membership, output shape and conservative call/effect grants. Check expressions in step order: BIND value; CALL arguments by ASCII name, then handlers by ASCII code and their fields by ASCII name; root return fields last. Each expression completes typing/overlay/profile admission before the next. Aggregate AST counts include every handler, regardless of reachability. Existing safe diagnostics apply; use `ENTRY_GRANT_DENIED` for disallowed WRITE/effect counts and `DCM_INVALID` for unsupported lifecycle/key metadata. The one-write hard ceiling uses `BUDGET_EXCEEDED`; all failures emit no artifact.

## Closed DCM additions

The exact root and entrypoint forms in this section are effect/1. Effect/2–4 retain the hostKey/event type rules and post-commit lifecycle, while replacing required grants with optional hook restrictions as specified in the [generic-hook contract](generic-hook-capability-contract.md#effect4-contract-and-version-boundaries). Effect/3 and effect/4 use their respective assurance values from the version table above.

The root is exactly `{format,domain,types,capabilities,entrypoints,hostKey,assurance}`. `assurance` must be `SIMULATION_ONLY` for effect/1; it is a restriction, not a certification. `hostKey` is exactly `{source,type}`: source must be `requestKey`; type is a nonempty string bounded to 256 UTF-8 bytes identifying an exact host-native key contract. It is **not** a business/CEL type and cannot be referenced as a key contract by source parameters, record fields, literals or descriptors. Its label belongs to a separate namespace: equality with `String`, `Boolean` or a declared business type name is permitted and creates no type alias, conversion or access to the key. Business references resolve only against built-ins/DCM types, never `hostKey.type`. One binding only, shared by all calls in this invocation.

Capability fields are unchanged except `effect` accepts `READ` or `WRITE`. The root key and entrypoint event context are supplied to both kinds through the protected adapter channel below, never merged into `parameters`. Existing scalar `binding:host` parameters remain supported. WRITE responses must obey the effect outcomes below. All business error codes remain stable declared strings; this profile caps each capability's errors at 16.

Entrypoint is exactly `{input,output,trigger,placement,consumer,grants,effectGrant,event}`. Require `trigger:EVENT`, `placement:AFTER_COMMIT`, and consumer `{id,version,kind:EVENT_REPORT}`. `effectGrant` is integer 0 or 1. `event` is exactly `{idType,sourceType}`, both naming declared nominal String types. Per-capability grants remain positive integer call ceilings; omitted IDs grant zero. A zero effect grant admits no WRITE calls, even guarded ones. No pre-commit entrypoint is supported by this profile; reject `BEFORE_COMMIT` or other placements rather than enabling a write through the existence of a key. The read profile continues rejecting WRITE capabilities.

The host supplies an admitted event after the original operation committed. Nothing in the output can veto or roll back that operation. The generic runtime validates event types; the host and adapters enforce the relationship between the event source, business arguments and returned native entities. Source-selected project/title values are data, never authorization. Capability and consumer versions plus all new metadata are covered by the complete DCM digest.

## Artifact

Use the envelope for the selected version from [compiler-artifact](compiler-artifact.md), with its exact profile/format/model identity. The following CALL fields and definite expression environments are common to effect/1–4; `/1` embeds the model/descriptors and `/2`–`/4` reference the bound model. BIND is unchanged. CALL is `{op:CALL,id,capability,version,args,resultType,when?,onError?}`. `when` retains the checked earlier Boolean BIND ID. Each `onError` value lowers to `{type:outputType,fields:{field:loweredBinding,...}}`. Root return is unchanged. Allocate expression IDs in the source order defined above. Each `variables` map is exactly the definitely available environment for that position, including unused but available variables; guarded results are never inserted. Recompute and check these environments during preparation, rather than trusting artifact declarations.

Preparation independently checks guard/handler references, all type overlays, conservative calls/writes, lifecycle, key metadata and grants. No source interpretation or new opcode is needed. Unknown instructions/fields, forged effect classifications, omitted required checks or incompatible versions fail closed before callbacks or dispatch. Keep old golden bytes and rejection corpus unchanged.

Both loaders distinguish static effect authority from the hard ceiling: a WRITE exceeding the entrypoint's zero effect grant fails `ENTRY_GRANT_DENIED` at its `/artifact/steps/<index>`; a second possible WRITE fails `BUDGET_EXCEEDED`, regardless of guards.

## Host API and native key

This section preserves the legacy effect/1 API. Effect/2 relocates keyBinding to model binding; effect/3 adds qualification. Effect/4 uses [BoundEffect APIs](host-model-binding.md#api-shapes) with no key validator or authorizer callback and adds the absolute deadline to adapter context. The [original-key identity rule](real-single-effect-admission.md#effect-outcomes-and-key-identity) applies to every version.

For this profile only, admission extends the existing closed record with required `effectGrant` and `keyBinding`. `effectGrant` is 0 or 1, may only narrow the selected entrypoint, and must cover the artifact's conservative WRITE count. `keyBinding` is the host-only closed `{type,validate}` registration: type exactly matches `dcm.hostKey.type`; validate is a synchronous host function accepting one opaque value and returning Boolean. Snapshot its function reference and metadata during preparation. Do not invoke it at prepare time. Each adapter registration is exactly `{version,mode,keyType,invoke}`; `keyType` must equal `dcm.hostKey.type` for both READ and WRITE, otherwise preparation fails with `ADMISSION_INVALID` at `/admission/adapters`. Version, mode and keyBinding mismatches also fail preparation with `ADMISSION_INVALID` under `/admission`. All adapters and admission must have `mode:simulation`; reject `real` for this profile, even with supplied assertions or certificates. Real effect admission needs a separately reviewed host-evidence contract and compatibility change.

Invocation extends `{bindings,deadline,authorize,grants}` with required `{effectGrant,requestKey,event}`. Fresh effectGrant may only narrow admission (0 or 1); omission, widening or invalid form is `HOST_CONTEXT_INVALID`. Validate all invocation fields before any adapter call, including when the write will be skipped. `event` is exactly `{id,source}`, validated against the selected event nominal types, then copied as immutable scalar data. `requestKey` must be non-null and accepted by the snapshotted key validator; false, throw or non-Boolean result is `HOST_CONTEXT_INVALID`. No raw validation exception escapes. The host validator must be bounded, pure, and perform no I/O; deadline checks bracket it, with no hard preemption claim.

The runtime does not parse, stringify, hash, copy, freeze recursively, reconstruct or otherwise transform the key. The host supplies an immutable key value and owns its type, format, logical uniqueness, stability, collision scope and any wire serialization. In-process forwarding preserves the original value/reference to **both read and write adapters**; no execution/step/event ID substitutes for it. Across processes the host, outside Keir, owns lossless reconstruction of the same typed logical key. Prepared contains the validator, never an invocation key/event. No key/event values enter CEL, artifacts, public trace or error text.

The effect/1 adapter signature is `invoke(agentArgs, protectedArgs, remainingMs, hostContext)`, where hostContext is exactly `{requestKey,event}`. Snapshot/freeze the container and validated event scalars without traversing the opaque key. Existing read-profile adapters retain their three-argument contract. Java may expose the extra context as a small typed record and a separate adapter interface; no change to the old public invocation/adapter contract is required. Generic runtime must not route the key through scalar `Artifact.value` or protobuf conversion.

The sample host's key type is `sample.RequestUuid/1`: Java uses `java.util.UUID`; Node uses a host-created immutable branded value holding the same UUID logical value. A plain string or unbranded object fails the host validator. Only the host fixture loader constructs native values from test data. This is a sample host representation, not a new Keir scalar or a required UUID library. Tests assert that both adapters receive their invocation's exact original object/value and that neither runtime invokes conversion methods.

Before a reached dispatch: check remaining step/call budgets, current capability grant, current effectGrant for WRITE, arguments/protected bindings, current authorization, deadline and trace reserve. Invocation and per-call authorization request shapes remain unchanged; the host callback captures event/key/resource context. A zero fresh effectGrant is a valid narrowing: a reached WRITE fails `AUTHORITY_DENIED` before dispatch; a skipped WRITE performs no dynamic grant consumption. Static admission still counts all potential writes. Check effect permission before the per-call authorization callback. No retries, durable ledger or recovery API is introduced.

## Effect evidence and outcomes

READ adapter outcomes are unchanged and reject any `effect` field. WRITE has exactly these tagged shapes:

| Shape | Meaning |
| --- | --- |
| `{kind:SUCCESS,value:record,effect:CONFIRMED}` | Adapter attests a committed effect (including a confirmed duplicate result); validate record before using it. |
| `{kind:BUSINESS_REJECTION,code:declaredCode,effect:NONE}` | Definite rejection with no effect; terminal handler may run. |
| `{kind:TRANSIENT_FAILURE,effect:NONE}` | Adapter establishes no effect; FAILED/ADAPTER_TRANSIENT, no handler. |
| `{kind:UNKNOWN_COMMIT,effect:UNKNOWN}` | Commit unknown; UNCERTAIN/UNKNOWN_COMMIT, no handler/result. |

An HTTP status or local timeout is not effect evidence. After dispatch, throw/rejected future, timeout, malformed envelope or incompatible effect tag leaves UNKNOWN. A valid outer SUCCESS/CONFIRMED envelope establishes confirmation **before** validating its value: malformed/oversized value then fails with CONFIRMED retained, no bound result and no later step. A valid BUSINESS_REJECTION/NONE outer envelope establishes NONE even if its code is undeclared; the invalid code fails validation and cannot invoke a handler. Extra outer fields or invalid kind/effect combinations do not establish evidence. Late responses after timeout/termination cannot revise any result or receipt.

For both runtimes, settle the adapter-response/timeout race exactly once. If the response wins while the call is active, inspect its outer envelope and record valid CONFIRMED or NONE evidence **before** completion deadline/clock checks and result/code validation. This includes NONE from valid BUSINESS_REJECTION or TRANSIENT_FAILURE envelopes. A subsequent clock reading equal to expiry yields LIMIT_EXCEEDED/BUDGET_EXCEEDED; an invalid or regressing clock yields FAILED/HOST_CONTEXT_INVALID. Both retain the settled evidence, with no normal result, handler or later step. A wait helper must not discard the winning response by checking the completion clock before this evidence settlement. If timeout wins first, the receipt remains UNKNOWN and termination is UNCERTAIN/BUDGET_EXCEEDED; a later CONFIRMED or NONE response is ignored. Winning the response race preserves evidence, not permission to continue after expiry. Pre-dispatch deadline checks remain unchanged.

Outcome for this profile is `{classification,result?,error?,effects,trace}`. `effects` is always an array of zero or one closed `{step,capability,state}` records. A skipped or undispatched write has no record. Before invoking a WRITE adapter, record intent and initialize its receipt to UNKNOWN; replace only on validated adapter evidence. Every termination preserves that receipt. INTENT is a trace transition, not a final effect state. This is an in-memory receipt, not crash durability or proof that an external operation committed.

Classification rules:

- COMPLETED has a validated result and no error; any dispatched write must be CONFIRMED. The no-op path may complete with no effect.
- BUSINESS_REJECTION always retains `error:{code,path}` for the rejected call. Only a successfully evaluated matching handler adds a validated `result`; an unhandled rejection has no result. NONE is required for a rejected WRITE.
- FAILED or LIMIT_EXCEEDED has error and no result, retaining any CONFIRMED or NONE receipt. This includes return/handler validation, authorization, clock or trace failures after a confirmed write; never report rollback.
- If a dispatched write remains UNKNOWN, terminal classification is UNCERTAIN, even when the triggering code is BUDGET_EXCEEDED, ADAPTER_EXCEPTION, ADAPTER_INVALID or HOST_CONTEXT_INVALID. Retain that code/path in error and no result. No handler or subsequent step runs.

Handler evaluation failures use their ordinary classification/code/path, with `error.cause:{code,path}` retaining the original business rejection. `cause` is allowed only for this case, never recursive. Successful handlers keep the original error with no cause. Handler field paths are `/steps/<index>/onError/<escapedCode>/<escapedField>`; other paths retain existing conventions. Successful handler evaluation emits RETURNED then TERMINATED with the business error code. Limits, shape/type/Unicode order and safe error text otherwise follow the read contract.

## Trace and consumer

Extend the existing trace shape only with optional Boolean `taken` and effect `state`. A guarded CALL emits STEP_START then GUARD_EVALUATED `{step,taken}`; false adds STEP_SKIPPED and continues. True follows normal dispatch. WRITE emits EFFECT_INTENT `{step,capability}`, CALL_DISPATCHED, then EFFECT_RECORDED `{step,capability,state}` on settlement (including timeout). Valid successful result then emits CALL_SUCCEEDED. READ success and BIND events are unchanged. No skipped result is fabricated.

Before WRITE dispatch reserve five slots: EFFECT_INTENT, CALL_DISPATCHED, EFFECT_RECORDED, possible CALL_SUCCEEDED and TERMINATED. Before READ reserve CALL_DISPATCHED, possible CALL_SUCCEEDED and TERMINATED. No asynchronous work occurs between writing intent and invoking the adapter. If dispatch has not actually begun, local failure establishes no attempted effect; never claim UNKNOWN merely because a guard was true. Settlement updates the ledger before further validation/trace work; terminal capacity and the reserved effect record cannot be consumed by other events while the sequential call is pending. Later trace exhaustion preserves the ledger. Test the exact quota boundary. Trace contains no raw arguments, native keys, event IDs, resource values or exception details.

The EVENT_REPORT consumer returns a separate receipt `{status:REPORTED,classification,result?,error?,effects}` after validating the runtime outcome against this profile. It may display a handled BUSINESS_REJECTION result **as rejection**, never as success. For UNCERTAIN or failure it displays classification/error and retained effects without an ordinary result. It may show a CONFIRMED effect beside failed execution. It never changes the original committed event, creates a write, retries or infers an effect from a source-authored `CREATED` label. The read DISPLAY consumer remains COMPLETED-only. A malformed outcome yields `{status:NOT_REPORTED,code:OUTCOME_INVALID}`.

## Ordered simulation protocol and acceptance

The ordered stub, comparison and consumer rules below apply to all effect profiles. Select the exact scenario format for the selected artifact: `keir-scenario/effect-1`, `keir-scenario/effect-2`, `keir-scenario/effect-3` or `keir-scenario/effect-4`. Protected fixture construction uses that profile's host API; effect/4 fixtures supply no legacy grants, scope, key validator or authorizer.

Run the exact compiled bytes through the ordinary prepare/invoke path with explicit simulation registrations and the EVENT_REPORT consumer in **both** runtimes. Scenario data cannot supply executable callbacks, authorize real mode or change the plan. Use closed `{format,id,given,stubs,expect}` with the selected versioned format; `given` is `{input,fixture}`. `fixture` selects a trusted test-host fixture ID, not a filesystem path or callback. The host fixture constructs native key/event/bindings and deterministic clock behavior, plus any required legacy grants/authorization for its selected profile. Scenarios cannot override those protected fields. Ceiling: 65,536 raw bytes, four stubs; existing scalar/record bounds apply.

Each stub is `{step,capability,version,args,protectedArgs,response}` in exact dispatch order. `response` is one valid adapter outcome above; negative protocol tests inject malformed outcomes through the trusted test harness, not a permissive production adapter schema. Before consuming a stub, the test adapter checks actual capability/version and exact agent/protected arguments, and separately checks native key identity and protected origin against the selected fixture. The adapter context has no step label: after execution, reconcile captured calls with the trusted `CALL_DISPATCHED` trace entries by dispatch ordinal, require equal counts and capabilities, and compare each actual trace step with its stub's step. Derive reported `calls.step` from the trace, never from the expected stub or a second plan interpreter. A skipped call consumes no stub. Missing, extra, wrong-order, wrong-step, mismatched, or unconsumed stubs produce a failed simulation assertion outside runtime exception handling, even if execution otherwise returned COMPLETED. Do not turn a stub mismatch into a declared business rejection.

`expect` is exactly `{outcome,calls,consumption}`; outcome includes exact classification/result/error/effects/trace, calls is the ordered array of `{step,capability,version,args,protectedArgs}`, and consumption is the exact consumer receipt. Exclude real wall times. Harness diagnostics identify the mismatching field without leaking protected production values. Test clocks and fixture actions model timeout, denial and lost response without sleeps or live I/O. Duplicate delivery is explicitly simulated; it is not certification of real atomic deduplication or retention. No production activation path is added.

The [shared conformance corpus](../../conformance/generic-hooks/README.md) and [testing evidence](../testing.md) identify the versioned vectors. Preserve earlier profile regression fixtures and packaged-host behavior. Simulation does not establish real persistence, authority implementation, duplicate suppression, hard deadlines, exactly-once execution or recovery. Host implementations own native guarantees; effect/3 additionally retains its explicit [qualification protocol](real-single-effect-admission.md#legacy-effect3-qualification).
