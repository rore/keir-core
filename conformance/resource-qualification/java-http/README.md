# Java HTTP capacity diagnostic

This opt-in benchmark puts a prepared Java Keir program behind a small loopback HTTP host and compares it with manual native logic. It measures a stated synthetic workload on a stated host. It does not establish a maximum supported request rate, user count or production SLA.

The [compact results](results.json) retain every stage of the new sample, including cold/warmup, failed screens, overload and recovery. The code and results here are a new implementation and execution. They do not reproduce or directly revalidate the earlier HTTP diagnostic described below.

## Reproduce

Use Linux, Java 21 and Node 24 in an isolated checkout. Build the current compiler and teaching host with repository-local Maven caches, then run from the repository root:

```sh
MAVEN_USER_HOME="$PWD/.tools/maven" ./mvnw -o -B -ntp \
  -Dmaven.repo.local=.tools/maven/repository -DskipTests package
taskset -c 2,3 node conformance/resource-qualification/java-http/run.mjs --smoke
taskset -c 2,3 node conformance/resource-qualification/java-http/run.mjs --sample
```

Omit `-o` only if the isolated cache needs ordinary dependency resolution. The measured image had the Java 21 compiler module but lacked the `javac` launcher and release metadata. Its successful build additionally used `-Dmaven.compiler.release= -Dmaven.compiler.source=21 -Dmaven.compiler.target=21`. The harness invokes the same compiler module directly; no global tool installation is needed.

The default host affinity is CPUs 0 and 1; the command above restricts the generator to CPUs 2 and 3. Choose two available host CPUs with the command-local `KEIR_HTTP_CPUS` variable if necessary, and select separate generator CPUs with `taskset`. The harness records and verifies actual host affinity. Affinity restricts where work runs; it does not reserve CPUs. The generator, sampler and server still share the machine and any cgroup quota.

Each run writes its report, raw latency/dispatch samples, generated inputs/artifacts, compiled probe and bounded child output under a new ignored `build/java-http-*` directory. It never overwrites committed results. Retain failed runs when evaluating a change; copy only inspected compact evidence into Git. Rebuild after changing Core, and record a new source/harness identity. The historical results below cannot be regenerated by this new harness.

The recorded primary run at commit `432307b5ff570ecec83946a60377e40c108bbf4e` stopped after a dense confirmation had two transport failures. That failed run is preserved. The subsequent control-only change records transport error codes and retains reconciled transport failures as failed capacity screens while continuing collection; incorrect outcomes/counter mismatches and resource breaches still stop the run. Smoke still requires every offered request to succeed. The targeted `--followup` command runs a lower-rate ordinary pair, the missing native dense baseline, slow callbacks and recovery, rather than repeating the whole sample. The Java host, Core source trees, fixtures and built binaries are unchanged between these two runs; their distinct source/harness hashes remain in the results.

## Work and comparison boundary

The ordinary program is the current [four-step follow-up fixture](../../keir-3/source.yaml). Every successful invocation reads a task and confirms one simulated write. Each callback is scheduled after 2 ms in the main comparison. Every request gets fresh input, actor/event values and an opaque native key; callbacks check their identity, order, protected bindings, arguments and remaining budget. There is no authorization lookup, real database/network request, idempotency transaction or durable effect.

The dense program is generated from the current [Inventory model](../../keir-3/dcm-inventory.json) and [maximum no-match input](../../keir-3/scenarios/inventory/inventory-max-no-match.json). Eight reached LETs each evaluate ten false membership tests over sixteen 256-byte labels. The compiler output is checked for exact operators/selects, 473 nodes and depth 7. Source semantics imply 80 scans and 1,280 element visits; no instrumented operator counter is installed. No adapter is called. This is substantial synthetic evaluation, not a universal worst case.

Compilation, model binding and preparation happen before the host announces readiness. One prepared artifact per rule is reused. The ordinary artifact must match the current pinned fixture byte for byte. Every Keir result is serialized and compared with a complete independently supplied expected outcome and trace. The dense expectation is constructed separately from the evaluator; the ordinary expectation comes from shared conformance. An intentionally incorrect expectation must produce HTTP 500 before measurements begin.

The native control manually performs the same business logic and controlled callbacks, constructs the full outcome/trace, and uses the same serialization/assertion boundary. Both engines share HTTP parsing, response construction, the 32-slot semaphore and telemetry. The JDK HTTP host enables TCP_NODELAY. The comparison includes HTTP, host scheduling, diagnostic assertions and framework integration overhead; it does not isolate CEL evaluation cost. Native dense loops implement the same membership semantics without Keir admission, typing or runtime machinery.

## Scheduling, accounting and limits

Arrivals follow an independent monotonic constant-rate schedule. Success latency runs from planned arrival through complete response parsing, including dispatch lag, HTTP/host waiting, invocation and diagnostic checks. Nearest-rank p95/p99 are recorded for successful responses, all HTTP responses and dispatch lag. A 512-outstanding generator guard drops arrivals visibly; these are generator drops, not HTTP 503 responses. Each request has an absolute five-second deadline, including connection/agent waiting. After arrivals stop, the bounded drain is included in the reported elapsed throughput. Every offered arrival is reconciled with correct success, explicit busy, generator drop, transport error or incorrect response, and server counters are cross-checked.

A clean diagnostic screen requires all offered arrivals to succeed, success p99 below 50 ms and dispatch-lag p99 below 10 ms. This is a screening choice, not a product SLA. Ramps select a rate for a 30-second Keir/native pair per rule. Collection `status: completed` means the collection checks passed; each stage's `capacityScreen` separately states whether that screen passed. Failed confirmations remain failed evidence. The original primary run's two transport errors were not categorized further, so their cause remains unresolved.

The Java host uses two-CPU affinity, `-XX:ActiveProcessorCount=2` and `-Xmx512m`. The heap cap does not cap process memory. A 100 ms `/proc` RSS sampler kills the direct JVM on an observed 1 GiB breach. This is sampled observation with a kill response, not hard memory containment; brief peaks can escape sampling. Heap before/after and 100 ms sampled peak heap are recorded without forced GC. These do not measure allocation rate or prove leak freedom. CPU is whole-process CPU time divided by elapsed stage time; shared cgroup throttle counters can include other processes.

Only 32 operations are admitted concurrently. The semaphore does not bound HTTP ingress, sockets, runnable virtual threads or pre-handler backlog. CPU-bound work may wait before reaching it. `peakAdmitted` measures admitted operations; it does not locate or measure queue depth. Every child has a finite watchdog and 1 MiB combined output cap. The server has a 300-second watchdog; `--sample` schedules 171 seconds of arrivals plus bounded drains/setup, and `--followup` schedules 108 seconds. The retained primary stopped after 129 seconds; primary plus follow-up therefore scheduled 237 seconds. Smoke uses ten requests/second, one second per engine/rule and a four-outstanding guard. Normal shutdown verifies executor termination, zero active operations/pending callbacks and returned permits. A separate idle instance of the actual Java HTTP server is deliberately timed out, reaped and checked for port release. The failed primary was killed and reaped by failure cleanup; it did not reach the graceful-shutdown/port-release probes.

## Fresh recorded sample

The fresh run used an Intel Xeon Platinum 8573C host with five visible logical CPUs, Java 21.0.13 and Node 24.22.1. The shared cgroup had a four-core quota (`400000 100000`) and 16 GiB memory limit; Java ran on CPUs 0–1 and the generator/sampler on 2–3. This was not an exclusive two-vCPU allocation. Core compiler/runtime source trees were unchanged from main `d484c46cc416ad98aa4753d6759586d48d833e01`. Measured harness commits were `432307b5ff570ecec83946a60377e40c108bbf4e` and the follow-up commit identified in the JSON. Harness, binary, fixture and generated artifact hashes are recorded per run.

| 30-second configuration | Correct / offered | Busy / transport errors | Success p95 / p99 | Mean occupied cores | Sampled peak RSS | Clean screen |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Primary: Keir ordinary, 1,200/s | 35,789 / 36,000 | 211 / 0 | 7.5723 / 12.4464 ms | 0.5053 | 287.82 MiB | Failed |
| Primary: native ordinary, 1,200/s | 35,823 / 36,000 | 177 / 0 | 6.4237 / 8.8652 ms | 0.2580 | 288.36 MiB | Failed |
| Primary: Keir dense, 600/s | 17,998 / 18,000 | 0 / 2 | 197.0590 / 418.7825 ms | 1.1540 | 291.90 MiB | Failed |
| Follow-up: Keir ordinary, 300/s | 9,000 / 9,000 | 0 / 0 | 8.8727 / 12.7750 ms | 0.4866 | 268.52 MiB | Passed |
| Follow-up: native ordinary, 300/s | 8,996 / 9,000 | 4 / 0 | 7.5273 / 31.6150 ms | 0.1663 | 270.61 MiB | Failed |
| Follow-up: native dense, 600/s | 18,000 / 18,000 | 0 / 0 | 1.5094 / 2.6971 ms | 0.1013 | 266.04 MiB | Passed |

All six confirmation rows had zero generator drops and zero incorrect outcomes. The clean ordinary 300/s Keir point is a tested point, not a maximum. The native dense baseline ran in the follow-up JVM, separately from the primary Keir dense run. Run order, JIT/GC state and shared overhead prevent treating these differences as isolated framework cost or inferring a performance advantage from small busy-count differences.

The short ordinary 600/s ramp returned ten busy responses while its later 1,200/s ramp passed; ramps were not monotonic. Dense ramps at 1,200/s and 2,400/s dropped 607 and 5,549 arrivals at the generator guard, with success p99 about 681 and 694 ms. Both failed their screens. Cold Keir ordinary/dense warmups reached about 81/111 ms p99. Native warmups also exceeded the screen at some points. All phases remain in the JSON.

With two 20 ms callbacks, the six-second 1,200/s stage completed 4,604 of 7,200 arrivals, returning 2,596 busy responses with no generator drops. Success p99 was 48.0585 ms and mean CPU occupancy 0.3824 cores: waiting/host admission limited this synthetic workload despite low average CPU. The subsequent 100/s recovery completed all 300 requests correctly, with zero active operations/pending callbacks at drain, but its 64.6617 ms success p99 and 29.3976 ms dispatch-lag p99 failed the latency screen. The follow-up therefore retained `status: failed`; it did not reach graceful shutdown probes. Both measured runs were killed/reaped on failure, while the separate strict smoke runs verified graceful shutdown, actual-server timeout cleanup and port release. No observed RSS watchdog breach occurred.

The two load runs scheduled 237 seconds and reconciled 173,100 arrivals: 163,689 correct, 3,253 busy, 6,156 generator drops, two transport errors and zero incorrect outcomes. Commissioning failures are retained separately as corrected harness defects. Raw nearest-rank percentiles, arithmetic, hashes and child-close receipts were checked locally. These are one trial per configuration, not a long soak; neither failed collection is represented as an overall successful capacity qualification. Different hardware, host code and assertion boundaries also prevent attributing differences from the earlier diagnostic to runtime hardening. Repeat the diagnostic on the actual application host with real dependencies and its latency/error targets before making a deployment decision.

## Earlier author-reported diagnostic

The original author reported the following results on pre-hardening Core `566caa4d4b826dc87e6493090bd5a53672dc26f0`. That diagnostic used Java 21.0.13, Node 24.22.1 and a Linux AMD EPYC 9V74 host. Java affinity was CPUs 0–1 with `ActiveProcessorCount=2`; the generator used 2–3 and sampler 4. This was not an exclusive two-vCPU VM. The Java heap cap was 512 MiB, with a 1 GiB observed-RSS watchdog.

| Warm 60-second configuration | Correct / offered | Busy responses | Success p95 / p99 | Mean occupied cores | Sampled peak RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| Keir ordinary, 600/s, two 2 ms callbacks | 36,000 / 36,000 | 0 | 6.2471 / 8.1632 ms | 0.229 | 188.2 MiB |
| Keir ordinary, 1,200/s | 71,986 / 72,000 | 14 | 6.3953 / 9.3855 ms | 0.364 | 187.2 MiB |
| Native ordinary, 1,200/s | 71,978 / 72,000 | 22 | 6.3198 / 8.6454 ms | 0.212 | 164.0 MiB |
| Keir dense, 1,200/s | 72,000 / 72,000 | 0 | 3.9098 / 8.2210 ms | 0.977 | 191.4 MiB |
| Native dense, 1,200/s | 72,000 / 72,000 | 0 | 1.8012 / 2.9836 ms | 0.177 | 151.5 MiB |

The author reported zero mismatches, invocation failures, transport errors and generator drops in those steady rows. Both ordinary 1,200/s rows fail the all-success screen. The difference between 14 and 22 busy responses in one trial establishes no performance advantage. The clean 600/s ordinary and 1,200/s dense points are tested points, not maxima.

The earlier dense 2,400/s stage completed 18,750 of 19,200 arrivals, dropped 450 at the generator guard, occupied 1.890 cores and reached 259.44 ms success p99. It had no server 503; its peak admitted count of two was consistent with pre-handler backlog, not direct queue measurement. Ordinary 2,400/s returned 69 busy responses among 19,200 arrivals, with 12.40 ms success p99 and 0.621 cores. Some 4,800/s stages had excessive generator lag/drops; passing ramp points were not monotonic, and the native immediate baseline passed its short screen. No maximum supported rate follows.

With two 20 ms callbacks at 1,200/s, the earlier host completed 6,010 of 9,600 arrivals over eight seconds, returned 3,590 busy responses and had no generator drops. Success p99 was 57.11 ms at 0.377 cores; dependency waiting and the 32 slots dominated. Recovery at 100/s succeeded. Cold warmup sometimes rejected ordinary requests; dense warmup p99 reached roughly 158–264 ms.

The original author validated the retained dataset, reporting 68 stages, 864,100 offered, 854,758 correct, 8,708 busy and 634 generator drops, with no resource-watchdog breach. **This integration has not directly inspected or independently revalidated that dataset or its harness.** Its separately retained archive is named `keir-java-web-capacity-results.zip`, SHA-256 `328e7d73dc32e90aea4a16cbf332da41d0346159f7f0bc936af466bca4b5df65`. Old raw samples are not published here. Neither diagnostic is a long soak, real-database qualification, multi-replica result, hard containment proof or consumer-user limit.
