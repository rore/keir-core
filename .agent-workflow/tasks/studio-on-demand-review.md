## Concrete technical plan

The accepted c017 brief owns product behavior. Reuse the existing one-owner lifecycle and shell; a general front door does not require a generic registry, another controller or new customization instances.

1. **Collection and start.** Keep collection state separate from read success: loading, failed/retry, known items and untouched empty are distinct. With a successful current-owner response, an item is known when selection, draft, retained history/evidence or positive selection generation records prior use; an off item is never dropped merely because selection is null. New customization is available once owner context is established, including while the collection read needs recovery. Workspace opens Studio with a start intent and the correct return target. Start shows the general question, an inline available-starting-points action and a disabled Create from a description control labelled To be implemented with visible accessible reason. It accepts no free-form submission and performs no lifecycle POST. Discovery reads the real catalog/state: unapproved draft offers Continue draft; saved selection or approved choice offers Open existing setup; off/no-draft offers Set up. All reach the same owner-scoped item and retain history. Collection items offer Open or Continue draft. Missing catalog data is Unavailable/retry, never an invented working template.
2. **One controller, saved choices.** Keep Studio's serialized operations, trusted-state gating, mounted/serial fences, uncertainty reconciliation and Workspace selection invalidation. Transition from start/discovery to the existing item without loading a draft implicitly. Place catalog buttons under the current conversation question rather than in a detached permanent choice strip. Only a successful draft response adds the person's choice receipt and its consequence, bound to that returned revision; failed or superseded requests do not claim success. Keep bounded visit-local messages; earlier choice controls become receipts and cannot mutate a new proposal. Retain current In use/Off/Unavailable plus separate Proposed/Approved summary outside transcript scrolling. Change choice, View proposal and management remain reachable there when review is closed. Do not claim arbitrary chat authoring or persisted conversation.
3. **Review visibility and reading.** Add an explicit review-open flag independent of displayed evidence and the exact approval confirmation key. Default to a comfortable-width conversation. A simulator response offers its actual saved report count and evidence ID; it never opens review, moves focus or replaces the displayed earlier run. Explicit results/review/management actions open the existing pane and focus the relevant heading, retaining their invoker. Closing review preserves its mounted content, evidence ID, canvas/log positions, composer and preferred divider width, and returns focus to the invoker or current summary action if superseded. Explicit navigation advances the existing reading revision so late responses cannot undo it. On wide screens reuse the pointer/keyboard divider only while review is open; clamp effective width without destroying the preferred width on a narrow resize. On phone/short screens show conversation or review in the available workspace with Back to conversation. Hidden pane/divider controls are outside focus order. Local close and cached reading navigation remain usable while a request is pending; server actions retain trusted-state/serialization guards.
4. **Exact evidence, explanations and authority.** Explicit evidence links use their immutable saved ID and owner-scoped lookup. Approval still requires the current trusted draft/version, matching passing evidence and separate confirmation; typed approve/use requests only open review. Historical receipts/results cannot approve another revision and offer Return to current proposal. Explain each saved row beside its own expected/actual values, using neutral wording derived from that evidence; the completed-task example explains that the proposal applies to open tasks. Do not infer user authorship from prepared expectations. Historical text is never recomputed from the latest draft. Preserve explicit approval followed by separate Use and the ordinary adjacent/focused Use transition when the person has not deliberately changed reading. Exact approval-run recovery after remount remains the named unresolved contract issue below, not permission to substitute the latest run.
5. **Native return and lifecycle management.** Preserve the existing native detail suspension, title/notes draft, original return invoker and current-owner/current-task checks. Keep saved status separate from unsaved fields when checking real task advice. Management opens the existing disable, eligible restore, history and recovery controls from the persistent summary; show owner, provenance and outcome before restore. Refresh saved state on item re-entry, clear all visit-local state on owner change and retain cross-tab/session/generation fencing. Reconcile uncertain mutations before another consequential action. No new mutations, IDs, capability execution or data stores are proposed.
6. **Verify the functional change after approval.** Extend existing real browser fixtures and the five designer journeys rather than build another prototype or server. Preserve functional checks that already protect late responses, exact evidence, explicit approval/use, native edits and scroll isolation. Use the Verification plan above, record actual focused/full results and have the designer inspect the rendered app. Fresh complete-diff risk and independent result review follow implementation. Manager alone integrates, refreshes the stable preview, runs hosted qualification and closes delivery.

## Approval-evidence readback issue

The isolated in-memory API probe exercised real Fastify routes without a listener or persistent database. `GET /api/extensions` distinguishes untouched versus known/off state and does not mutate it. The normal draft, simulate A, approve A, leave/read and `GET /api/extensions/evidence/:id` path reopens the exact six-case run.

For the same revision, a later simulate B returns `approved=true` with `evidence=B`, while the stored approval still binds A. `src/extension-lifecycle.mjs` exposes the latest evidence and approval boolean in state; immutable evidence lookup exposes no approval relation. The bounded evidence list cannot identify A reliably. Consequently a frontend-only plan must not call latest B the approved run or infer approval binding from order or pass status. An architect consult requests a supported existing-API resolution or a task-owner decision about a separately scoped read-model change. No such backend change is authorized here. Continue unaffected presentation planning; keep this mechanism and implementation readiness blocked until resolved.
