### Loop and host contracts

Export a small `runAuthoringTurn({ provider, host, context, state, input, signal, limits })`. The caller supplies and persists the owner-scoped state, conversation ID and accumulated counters. The provider exposes one bounded completion operation over host-built messages/tools plus private native continuation; it returns validated tool calls, user-facing text, usage and a stop reason. Only the host writes conversation state. UI text is inert text, never generated HTML/code. One active run per owner/conversation prevents duplicate dispatch; an input operation ID and expected conversation version reject duplicate/stale submissions. User switching or cancellation invalidates the run token and late results.

Proposed host callbacks below are contracts for agreement with the authored-draft owner, not claims about existing exported APIs. `context` is a host-created, nonserializable owner/session/current-authority handle and captures the selected DCM/profile/compiler/fixture/consumer identities; the model never supplies it. `signal` is host cancellation. Each callback validates ownership and version at entry and atomically before persistence, including after awaited work.

| Callback | Inputs and result |
| --- | --- |
| `discover(context)` | Returns only the scoped host-approved catalog, hook/types, supported profile, limits, current draft/scenario versions and safe identities; no protected bindings or credentials. |
| `saveDraft(context, {sourceBytes, expectedDraftVersion})` | Retains a new immutable candidate source and returns its host revision ID and new draft version. A stale version does not overwrite current work. Invalid source may remain a failed candidate; no eligible artifact is invented. |
| `compile(context, {revisionId}, signal)` | Compiles those exact retained bytes against host-selected DCM/profile through the packaged bounded Java wrapper. Returns safe diagnostics or exact source/model/artifact/compiler identities tied to that revision. Never accepts a path, executable, DCM or artifact from the model. |
| `replaceScenarios(context, {revisionId, casesBytes, expectedScenarioVersion})` | Validates and retains an immutable independent suite for that exact owned revision. Returns host scenario revision/version and digest. No observed-result-to-expectation copying. |
| `simulate(context, {revisionId, scenarioRevisionId}, signal)` | Runs those exact compiled bytes and cases through actual read simulation with host fixtures and current authority, then persists exact complete evidence only if the owner/session/draft/suite are still current. |
| `readEvidence(context)` | Resolves the current owned revision, suite and completed run from trusted storage and returns their exact identity, reports, eligibility and review display. No model-supplied evidence ID or success assertion. |

Six closed model tools: `discover_catalog({})`, `ask_clarification({question})`, `compile_draft({sourceJson,expectedDraftVersion})`, `replace_scenarios({revisionId,casesJson,expectedScenarioVersion})`, `simulate_draft({revisionId,scenarioRevisionId})`, and `offer_review({summary})`. Required fields and `additionalProperties:false` apply to every tool object. Host validation precedes callbacks; source/cases travel as bounded JSON strings to avoid a large generated DCM schema in provider tools, then native boundaries validate their contents. `compile_draft` composes saveDraft and compile using the actual returned revision; after compiler failure, any repair is a new immutable candidate with the current expected version. No callback can approve, activate, edit the DCM or invoke a live task adapter.

Clarification emits an awaiting-user event and stops active processing without inventing a reply. `offer_review` calls readEvidence with host context and builds its identity/eligibility from trusted storage; the summary cannot choose a run, invent a digest or turn a failure into success. An ineligible/mismatching run may be explained, but the host does not expose an eligible approval action. Approve and Use remain separate existing human actions with exact lifecycle guards.

### Scenario and evidence policy

Accept 1–8 strict `keir-read-simulation/1` cases, unique IDs and at least one intended-behavior case under the normal permitted host fixture. An expected business rejection under permitted entry is valid. Every submitted case must PASS; MISMATCH, INVALID_SCENARIO, SETUP_ERROR, CONSUMER_ERROR, partial/cancelled or missing reports cannot produce eligible evidence. Zero-call cases use empty stubs/calls and still observe host entry authorization. Repeated reads use actual static step IDs and ordered arguments/responses up to the native ceiling; unused stubs fail. Never require a sample template's call list, classification or DONE mapping.

Store source revision/digest, canonical case bytes/digests and expected calls/outcome/receipt separately from actual reports. Bind exact compiler, DCM, artifact, fixture, consumer, suite and completed run identities. Changes require fresh evidence and applicable renewed human review/approval. The AI may propose expectations but cannot independently certify them or silently rewrite them from actuals. Review shows exercised cases and untested limits. Host authority/denial/resource regressions protect the integration separately from the customer suite. Public reports retain the existing redaction contract; private trace/result values are not reconstructed from error text.

### Finite resources, failures and cancellation

Initial reviewable host authoring defaults: at most 8 generation calls and 8 tool dispatches, 3 compile attempts, 2 complete simulations and 2 clarification pauses per authoring run; at most 8 user continuations. Counters survive pause/resume and duplicate requests. A new run is explicit and consumes the same owner/session spend envelope, rather than resetting a quota through rephrasing. One in-flight run per conversation, at most 2 provider requests and 1 compiler child globally. Active processing is capped at 120 seconds total; each outbound request at 30 seconds. Human waiting is excluded; inactive conversations expire after 24 hours with a clear restart path.

Source is at most 16 KiB; a suite at most 48 KiB total and 8 cases, with each case also subject to existing native 64 KiB/depth-16/4-call limits. Each serialized provider request, including tools and continuation, and each provider response is at most 128 KiB; total retained conversation content is at most 256 KiB. Each generated response has at most 4096 output tokens, including billed reasoning. These are explicit AI authoring quotas, not changes to native/manual compiler acceptance. Do not silently truncate source, identities or cases. Read response bytes incrementally even without a truthful Content-Length and abort on overflow. Check limits before JSON parsing and dispatch.

Unknown tool/name, invalid fields/types, duplicate call IDs, multiple tool calls despite serial selection, unsupported response blocks, refusal or incomplete/token-limited output never dispatch. Safe argument errors consume quota and may be reported to the model within the remaining finite budget. Compiler diagnostics alone are normal bounded repair input. Unexpected tool throws, stale ownership/version, provider authentication failure, rate limit, server failure, malformed transport or ambiguous network failure stop with a safe typed blocker; no automatic retry or replay of a possibly completed call. Do not expose raw provider/compiler exceptions or HTTP bodies.

Cancellation aborts fetch and its reader and propagates to the compiler wrapper, which must terminate and reap its own child. Recheck owner/session/run/revision before committing or displaying any late result. AbortSignal does not preempt synchronous simulation; preserve native quotas/deadline and reject stale completion. Partial compile/simulation never becomes approval evidence. An immutable candidate already committed before cancellation may remain, explicitly unapproved, and readback reconciles actual state.

### Spend and configuration

Require an explicit finite operator `maxUSD` before any paid operation, a selected qualified provider/model and a conservative per-generation reservation derived from the bounded input/output allowance and the configured model tariff. Initially reserve 135,168 input tokens and 4096 output tokens per generation: one input token per allowed serialized request byte plus 4096 for protocol overhead. This is a conservative model-qualified accounting assumption, not a tokenizer theorem; qualification must reject or increase an insufficient allowance before enabling that configuration. Reserve at most eight such requests from the same owner/session envelope, check actual returned token usage and stop if it exceeds the qualified allowance. Atomically reserve before each generation and stop before dispatch if insufficient. Keep the entire reservation after timeout, cancellation or missing usage; no automatic refund/retry. Record safe token/call counters and known usage only. Treat application accounting as conservative budget control, not a literal provider invoice guarantee; use a provider-side hard account cap when that guarantee is required. Do not add a billing subsystem, mandatory token-count HTTP request per turn or speculative tokenizer dependency. Recheck the chosen allowance/tariff during live qualification; inability to establish a conservative reservation blocks paid mode.

The server alone loads provider enum, exact model, key, finite cap and rates/reservation policy from process environment or ignored local configuration. Read credentials only when the configured provider is intentionally created. `.env.example` contains placeholders such as `KEIR_AI_PROVIDER`, `KEIR_AI_MODEL`, `KEIR_AI_MAX_USD` and provider key variables. No browser credentials/config override, model-selected URL, user baseURL or automatic provider/model fallback. Fetch uses fixed official HTTPS origins and rejects redirects. Missing/invalid setup returns an AI-unavailable state without affecting native tasks, manual source authoring or already active extensions.

Only the explicit authoring conversation, scoped public contract, authored source, synthetic scenarios and sanitized compiler/simulation results go to the provider. Do not send cookies, keys, internal paths, protected bindings, real task records, DB dumps or unrelated user data. Do not log prompts, secrets, source/scenario payloads or raw responses. Treat user/provider/source/tool text as untrusted data; permissions and a closed tool registry enforce authority independently of prompts. No environment changes or paid calls occur during planning.

### Host bridge and Studio dependency

Persist owner-scoped conversation messages, safe events, expected version, run token/state and finite counters through existing storage conventions. Disallow cross-owner reads and reject old session/run responses both server-side and in the existing UI guards. On restart, an in-flight run becomes interrupted; never replay an uncertain paid/tool call. Preserve draft/source and task unsaved edits, reading position and optional review surface. Add only idle, running, awaiting clarification, review available, cancelled/blocked and AI-unavailable interactions to the accepted chat flow. User responses and canvas edits enter as explicit new user input; no hidden confirmation or forced wizard.

The existing app has a 24 KiB body limit and 10-second request timeout. Use a route-local short start/continue request that creates an owned run, then bounded owner-authorized readback and an explicit cancel operation; do not hold a 120-second AI request open under existing settings or raise global limits. The bridge owner confirms exact routes and transport after the authored-draft plan; polling is bounded to one active conversation and stops on terminal state/unmount/session change. Shared-file integration must preserve no-store, same-origin/CSRF/session checks, response limits and manual behavior. A more involved job framework or streaming transport requires a reviewed reason.
