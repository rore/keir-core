## In Scope

- Design integer and decimal values across host inputs, capability arguments/results, bindings, outputs, expressions, DCM, source, artifacts and host APIs. Specify ranges, precision/scale, exact wire and engine representations, validation and canonicalization.
- Specify comparisons and assess addition, subtraction, multiplication and division against concrete business needs. Define overflow, zero division, non-terminating division, rounding and invalid-value behavior before recommending the release boundary. Neither smaller implementation alone nor plausible usefulness alone settles inclusion.
- Define numeric literal syntax, integer/decimal interaction, comparison, promotion and conversion rules without silent precision loss or surprising coercion. State whether nominal numeric types, units or currency consistency are enforced.
- Evaluate bounded list length for an actual supplied bounded list, explicitly separate from a query's total matching record count. Explain its semantics, costs and release recommendation.
- Preserve optional-presence and guarded-result proof rules, lazy branches, failure/effect evidence, original host authority, computation bounds and prior approved artifact behavior.
- Plan at least two domain-neutral Core examples, including a stock/quantity threshold and a percentage or amount rule. Hosts supply business data and approved operations; Core does not supply those services.
- Assess a natural Daymark example against actual hooks/data. If justified, plan the complete Studio, simulation, approval, separate activation and runtime journey. Do not invent domain fields or claim a fixture establishes that journey.
- Specify schema/format/producer/package compatibility, old-artifact execution and approval retention, installed Java/Node consumer qualification, numeric boundary/invalid/error/optional/guarded conformance and bounded resource checks.
- Plan updates to affected language/DCM/runtime specifications, schemas, authoring guidance/companion and concise human-facing examples. Use release numbers only where compatibility or this release plan needs them.
- Define and qualify exact Java/Node normalization helpers, realistic Decimal range/scale alternatives and old-profile compiler support before fixing the public contract. Include `0.00001 × 0.00001 = 0.0000000001` and explicit rounded intermediates.
- Use a small executable pinned-engine harness before full implementation. Compare nonnumeric, Integer and Decimal preparation, conversion, warm execution and concurrent workloads in both runtimes. Record latency, throughput, memory/allocation, machine and workload without arbitrary performance targets or whole-web-app claims.
- Keep a runnable Core Decimal example and a real tested Daymark Studio-to-native journey in the eventual 0.5 release scope. Deployment remains separate.

## Out of Scope

Changing immutable released schemas/guide/package bytes, automatic host upgrades or recompilation of approved extensions, unauthorized live demo/data/provider changes, execution forbidden by existing local holds, and weakening safety or correctness to obtain a green check. Ordinary source fixes, commits and bounded hosted verification are delegated; material new product/safety/environment decisions still need explicit resolution.

A full money/currency model, aggregate queries, general list transformations, multiple data-changing actions, generalized guard inference and a standalone Studio rewrite are not automatically adopted. Propose any only with a concrete requirement and justified design.

### Source assessment

The following source-only assessment records the original Core 0.4 baseline. Current implementation and executable evidence are recorded above; this historical assessment is not the present feature status.

- Current Core admits Boolean, String-based values and Timestamp, but rejects numeric business values and checked numeric ASTs. [Compiler expression checking](../../compiler-java/src/main/java/dev/keir/compiler/Expressions.java), [Java admission/evaluation](../../runtime-java/src/main/java/dev/keir/runtime/CheckedCel.java) and [Node admission/evaluation](../../runtime-node/src/cel.js) each need explicit numeric typing, conversion, operation and intermediate-bound rules. Ordinary CEL integer division truncates; mixed Node integer/double comparison can lose precision. Neither behavior is automatically suitable for the new contract.
- Canonical JSON numbers are currently bounded unsigned metadata, not business integers or decimals. [Compiler canonicalization](../../compiler-java/src/main/java/dev/keir/compiler/StrictData.java), [Java value handling](../../runtime-java/src/main/java/dev/keir/runtime/Artifact.java) and [Node validation](../../runtime-node/src/validation.js) require a deliberate exact public representation. A Decimal encoded like a String must not inherit concatenation or lexical ordering. A distinct internal bridge must be specified and qualified.
- The existing guarded-result implementation uses exact producer checks. A new profile must explicitly inherit its scalar proof/activation behavior while retaining rejection under old producers. `Integer` and `Decimal` are not reserved built-ins in old models; new reservations must not invalidate retained models or approvals. Restricted supplied-list length appears to be a low-incremental-risk Integer operation, but is not implemented or qualified by this assessment.
- Daymark's actual before-create proposal already carries a complete, required tag list with a native cap of eight distinct normalized tags. A new-task-only rule requiring notes above three tags is a natural planned Integer/list-length example. Normalization and distinctness belong to the host; Core length counts actual supplied elements. The rule would not apply to later edits or establish a total query count. There is no natural existing Daymark Decimal field; use runnable Core examples rather than add artificial task data.
- Daymark already has Studio, simulation, approval, separate activation and real native enforcement. Numeric/list-length recognition in the checked-artifact summary, new package/model/guide adoption, retained old/new model bindings and a complete authoring-to-native journey remain new acceptance work. Existing mocked Studio projections or direct compile-API tests alone cannot establish that complete journey.
