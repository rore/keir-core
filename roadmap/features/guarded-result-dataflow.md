## Summary

This Core capability increment lets a program use scalar fields from a successful conditional capability call when the same expression proves that its exact immutable guard is true. For example, conditionally create an acknowledgement and return its assigned reference; otherwise return an existing reference from input. The released contract excludes guarded results from later dataflow; this increment extends composition without widening effect authority.

The owner accepted this bounded increment after architecture consultation. The detailed contract, implementation, independent source reviews and bounded resource/source-compatibility evidence are complete. On 2026-11-12 actual installed Java/Node consumers and the edition-8 candidate companion passed hosted qualification; the manager verified the downloaded bytes and accepted the combined implementation/documentation result. The qualified package bytes and unchanged edition-8 archive are published on [Core 0.4.0](https://github.com/rore/keir-core/releases/tag/v0.4.0). Daymark adoption remains separate. It adds expressiveness rather than repeating the delivered customization journey.

## In Scope

- Permit scalar-field use only in the true arm of a conditional using the exact guard identifier governing the earlier call. Retain exact nominal, enum and timestamp types and existing same-expression presence checks for optional fields.
- Define and independently validate guard provenance in the compiler and runtime preparation. Retain successfully returned guarded values only within the existing bounded execution model; qualify lazy-branch behavior in both pinned engines.
- Preserve failure and effect semantics: rejection, timeout, malformed results and unknown outcomes do not become absence or select a fallback. The original single-write, step, call and expression ceilings remain unchanged.
- Select an explicit supported semantic/producer compatibility boundary, preserving all previously supported artifact tuples, identities and approvals. Update affected contracts, schemas, examples and authoring guidance alongside implementation.

## Out of Scope

Numeric types/arithmetic, collection predicates or transformations, nullable records, general predicate implication, proof transfer from a different guard alias, list/record-valued conditionals, implicit availability based only on a later call's guard, multiple effects, multiple bindings, new consumers and a workflow engine. No changes to the live demo or user environment are implied by this Core task.
