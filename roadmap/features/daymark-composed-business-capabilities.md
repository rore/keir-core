## Summary

In Personal and Team projects, people use the same Studio to ask for new behavior in plain language. The agent works out what the project supports and how to combine its capabilities. The person with permission reviews the proposed behavior and turns it on. People use it in the task screens they already know. Daymark still controls permissions and saved changes.

## Why

Today, a team that wants a process Daymark did not anticipate needs a new feature or has to enforce the process by hand. The product value is letting the team define the behavior itself. **Deliverable review is an example, not a feature template.** Changing the reviewer or title in the current demo is configuration, not authoring.

**Team adds collaboration, not a smaller automation product.** Personal and Team share the same task operations, fields, conditions, and events wherever those apply. Personal rules act on the owner's work. Team rules extend that base with project-member assignment and shared-task coordination, within the project's permissions. An exact restriction comes from authority or a native invariant, not from which examples a demo happened to use.

## Proposed product design

| Moment | What the user sees and does |
| --- | --- |
| **Create a project** | Open a focused **New project** form with a name and a clear **Personal / Team** choice. Do not insert the form into another project's task list. Save opens the new project; cancel returns to the original view. Add an existing teammate from the new project. |
| **Describe a process** | Open the same Studio from either scope, with a visible scope and one chronological chat. Scroll up to earlier turns without expanding a disclosure after each reply. Describe any desired behavior without choosing a template. The agent asks only questions that change what will happen. If part of the request is unsupported, it explains what's missing and gets agreement before narrowing or substituting. |
| **Review the proposal** | See one readable proposal, not separate compiler steps. Show each event, its conditions and actions, what carries over to the next step, and what happens when conditions do not match. Revise the behavior in plain language. Show examples specific to the proposal, including branches or dependencies that matter; keep exact rules and raw evidence in details. |
| **Make it active** | **Approve this draft** accepts the exact rules and their current examples. Turning it on is a separate choice. Put the draft and current behavior next to each other. If they overlap, show what stays, what gets combined, and what would be replaced. Never silently turn off an existing Personal customization. Editing or checking a draft does not affect active work. |
| **Do the work** | Use the normal task list and detail view. Show the useful result or next action, such as **Waiting for Leo to finish Review deliverable**, with a link. Daymark gets the current assignee, title, and link from the verified task relationship under the viewer's permissions. Do not bake those details into the rule's message. If a required review couldn't be created, explain that instead of saying someone is working on it. |

These requests illustrate the same authoring flow. They are not presets, a required pair, or the boundary of what Studio can author:

- **Deliverable review:** “For every new top-level task, create a linked review. Don't let the original task finish until that specific review is done.” In the intended experience, I do the review myself in Personal or choose Leo in Team. Finishing the review does not finish the original task. This exact gate works in the Team demo; Personal does not yet have the linked-task check or the ability to block completion.
- **Urgent intake:** “When someone adds a high-priority top-level task, create a linked triage task for Leo. Leave other tasks alone and don't block completion.” This uses the same native task operations with a different condition and no completion rule. It is an alternate request in the same Studio, not a second product journey or a template we ship. Reassigning the original task or setting its due date is a different request; it was shown against a fixture, not the current native Team catalog.

### How it works underneath

- **Keir authoring agent:** Daymark is a reference host, not the agent's domain. The same authoring logic and Keir guidance should work with another host's contract: understand the request, discover what's supported, ask before narrowing, compose Keir rules, and explain examples. Don't hardcode Daymark events, tools, fields, or workflows in that logic. The agent can propose rules and examples, not write live data, grant access, approve, or turn anything on.
- **Daymark host:** Maintain one source of truth for task primitives: events, readable fields, lookups, operations and their argument and effect contracts. Reuse the existing Keir model format. Derive the authoring and execution grants from that base using the scope and native authorization policy. Add Team grants for current project members and verified linked-task relationships. Do not copy Personal's access to owned private projects into Team. Daymark owns permissions, validation, storage, isolated examples, approval and activation, and native writes. Do not add an SDK, a separate product, or a Core runtime feature without a concrete gap.
- **Saved proposal:** Daymark validates the proposal against the selected scope's model and compiles each event rule the proposal uses. Save the sources, exact artifacts, and explicit event bindings as one immutable revision. The proposal must describe those saved rules. An intentionally absent completion rule is valid; a missing artifact for a required rule is not.
- **Examples and activation:** Use expectations from the agreed intent, not from copying what the executable did. Bind approval to the exact revision and its saved evidence. Replace the review template's fixed six examples with checks specific to the behavior being approved. Keep Team's single project selection and Personal's existing selections per event. A Personal proposal spanning several events turns on as one atomic change to the affected selections; unrelated ones stay on. For overlapping behavior, propose an explicit replacement or a combination the host can actually run. Do not pick an order that silently drops a rule or promises more writes than the host allows.
- **Execution:** Reuse the existing task hooks and native operations. For new multi-event behavior that follows a task through its lifetime, pin the revision at task creation. Keep existing Personal rules on their current execution path. To support the exact Personal review example, Daymark needs owner-scoped linked-task provenance, a completion check, and a way to keep the same revision across the two events. Those are host changes, not a second Studio or new Keir runtime. Daymark checks authority and owns every transaction. No AI runs during task work. Never retry an uncertain write.

### Build order

1. **Map the host contract before designing the next demo.** Inventory every Personal event, readable field, lookup, write and side effect. Identify what Team can reuse today, what needs native host work, and what must differ because of authority or a native invariant. Include before-save validation, post-create and post-completion rules, tag/title composition, due dates, lookup scope and updates that must not overwrite later human edits. A gap in the prototype is work to assess, not a permanent Team restriction.
2. **Design one path for new customizations.** Reuse the Keir loop and one Studio UI for transcript, composer, proposal, examples and decisions. Use one host authoring contract for event bindings, source and independent expectations. Derive checks from declared operations and agreed outcomes, not from a linked-review-specific offer shape or from observed execution. Keep scope-specific authority and commit checks in Daymark. Use existing native services where their guarantees match; do not grant Team access by reusing a Personal owner's identity.
3. **Plan compatibility before replacing either path.** Keep existing saved drafts, revisions, approvals, selections and in-flight Team pins readable and executable without reinterpreting them. Reuse exact-artifact checks, receipts, and Confirm → Approve → Turn on. Decide how new revisions interact with existing selections and old event pins before implementing the cutover. Known failure, no change and unconfirmed writes must remain distinct; never retry an uncertain write. No second engine or forced data migration.
4. **Prove composition and parity, then review the product.** Compare catalog grants and native outcomes across both scopes. Exercise the same common rule, different event/action combinations not used to design the implementation, and Team-only collaboration composed with a common action. Verify cross-project denial, member/admin rules, no recursive effects, and retained pins. Check the shared Studio on desktop and touch, including focused New project and continuous chat. Verify free-form authoring with a configured, capped synthetic build before owner review.

### Current split and redesign target

| Area | What is split today | What the redesign must establish |
| --- | --- | --- |
| Events | Personal has before-create, created and completed. Team has created and before-complete. | Share the common events with their existing decision or effect semantics. Add the linked-review completion gate where Daymark can substantiate it. A gate is not a substitute for an event after completion. |
| Task operations | Both models name `tasks.get` and `tasks.create`, but expose different data and arguments. Personal also has exact open-task lookup and source update. Team has linked-child lookup and linked creation with assignment, but no due date on creation. | Use the common read fields, creation fields, lookup and update behavior where authorized. Let a Team rule combine ordinary fields such as due date with an authorized assignee or link. Bound lookups and destinations to permitted projects. |
| Authoring and UI | The loop is shared, but Personal and Team still have separate offer formats and screens. The Team offer describes a narrow set of review outcomes. | Share the chat and proposal lifecycle, and make proposals describe supported event bindings and independent outcomes without referring to a demo workflow. Keep the legacy handlers for saved versions only as needed. |

- Prove the Team path with two different requests in that same conversation: high-priority triage with no completion rule, and linked review with a completion rule. These are examples of what the pipeline can accept, not buttons, special cases, or a fixed list of checks. Use offline responses for repeatable checks. - Exercise the same agent instructions and turn logic offline against one small non-Daymark host fixture. Swap only the contract and scoped tools; use a fixture with different event, field and action names. This checks the separation, not a second integration or live language understanding.
- Run the exact saved draft on isolated example tasks. Show the situation, result, and why in the main and expanded examples. ### Initial walkthrough reference

Keep **Customizations → New customization** and the existing Studio conversation. The project stays visible. **What can I ask for?** is optional help based on this project's actual capabilities, not a menu of workflows. Use the message box for both the original request and revisions.

1. **Ask.** “Create a linked review for each new top-level task. Give Leo two days to review it, and don't let the original task finish until the review is done.”
2. **Clarify in the conversation.** “I can create the linked review and require it before completion. This project can't set a due date on the review the rule creates. Should I leave the due date blank?” Keep the original request visible. Do not substitute a date in the title or silently drop the deadline. In Personal, explain that the linked review and completion hold aren't supported. Offer an ordinary follow-up after completion or leave the current behavior alone.
3. **Show one proposal after agreement.** “New top-level tasks get one linked review for Leo. The original can finish only after its own review is done. The review has no automatic due date.” Show a short example or two in the draft; let people open the rest. A mismatch or a missing required review stays visible. No linked task is not, by itself, proof the rule did not apply.
4. **Show the change before it goes on.** Keep **In use now** beside **This draft** in the conversation. Name any existing behavior the proposal would replace or combine. Put **Approve this draft** and, after approval, **Turn on for new tasks** in the same place. Show **Approved · Not on yet** between them. No activation from chat alone.
5. **Use Tasks as usual.** The original task says **Waiting for Leo to finish Review deliverable** with a link. Once the review is done, the original can be finished. No Studio visit for teammates.

Fold the scripted Team page into this flow rather than restyling it as a second authoring surface. Keep source, IDs, and traces in **Rule details**. Keep stop and emergency controls under **More**, with their different consequences clear before confirmation.

**Rendered draft feedback:** Keep the shared conversation, consent for unsupported requests, and separate approval and turn-on. Put one short proposal, its status, and the next decision together; put examples and answered questions below or behind a disclosure. The replacement consequence must still be visible beside **Turn on**. Use plain language for unsupported requests and offer only alternatives the selected scope can actually perform. Keep Studio controls off task screens. If no review is confirmed, say that instead of claiming the write did not happen. Emergency revocation stays available to admins for older revisions that can still affect work, even when nothing is selected.

Review one rendered walkthrough in both scopes before implementing it. Show an unsupported step and an overlap with existing behavior in the same flow. Judge whether a user can tell what will happen, who does what, and what is already in use without reading code or opening diagnostics. Distinguish the proposed experience from what each scope supports today. The design preview does not call a provider.

**Independent rendered review: draft 2 passed the interaction recheck, not visual sign-off.** The desktop and mobile captures put the proposal, current behavior, replacement note and next action in the first view. Personal asks before substituting an unlinked follow-up. Tasks shows the linked next step without Studio controls. The visual pass still needs simpler project controls, consistent typography and spacing, and more compact task cards. Preserve keyboard focus without boxing headings for mouse users. Don't show a disabled **Mark complete** button after completion. This is review of the scripted UX, not owner approval or proof of working authoring.

### Does the same design work for different requests?

Before settling the UI, compare these examples in the same conversation, proposal card, and examples disclosure. Use different requests to expose different decisions, not to define templates, a fixed number of examples, or a new mode. Reuse the reviewed review-handoff screen rather than redrawing it.

| Request | What the proposal says | What examples show |
| --- | --- | --- |
| **Personal · one action:** “When I finish a task here, create a follow-up.” | “Finishing a task in this project adds one task called Follow up.” Say whether finishing a follow-up also counts; ask only if that choice matters to the request. | “You finished Send brief → Follow up was added.” Show the created task, not a log entry. A task in another project is unchanged by this customization. |
| **Personal · branching and lookup:** “On high priority, make a follow-up only if none is open.” | “After you complete a high-priority task here, add Follow up if there isn't already an open one. If Daymark can't check, it adds nothing.” This checks for an existing task; it does not promise duplicates are impossible during simultaneous completions. | No open follow-up → added. One already open → kept. Normal priority → nothing added. Couldn't check → nothing added; say why. |
| **Personal · stop before save:** “Require notes on new tasks with more than three tags.” | “Four or more different tags need notes before you can save a new task. Existing tasks aren't affected.” | Four tags, no notes → not saved; tell the person what to add. With notes → allowed to save. Three tags, no notes → this rule doesn't stop the save. An allowed save is not a saved task receipt. |
| **Personal · two events in one customization:** “Require notes on new tasks with more than three tags. When I finish a high-priority task here, add a follow-up if there isn't one open.” | Two short lines under one name: **When you add a task** and **When you finish a task**. Each behavior exists individually; turning both on from one proposal is the proposed change. Show any overlapping customization beside Turn on. | Follow one task: save asks for notes → add notes → task saves → later finish it → Follow up is added if none is open. Show an existing-follow-up branch separately. |
| **Team · alternative paths or a handoff:** “Send high-priority tasks to Leo for triage, leave everything else alone.” Compare with “Wait for Leo to finish the linked review.” | “New high-priority tasks that aren't subtasks get a linked triage task for Leo; completion is unchanged.” Ask if “send” means reassign the original, which the Team rules can't do today. The handoff proposal instead says which linked task must be finished first. | Triage shows one matching and one unmatched task. Handoff shows the same original task before and after Leo finishes its specific review. If no review is confirmed, do not claim it was never created or offer a retry. |
| **Not supported, or not as requested:** “Remind Leo in two days if the review is still open,” or “Don't let me finish until I've done the linked review” in Personal. | “I can't schedule a reminder,” or “I can't hold completion on a linked review here.” Offer only a supported alternative and say what the user gives up. If no useful alternative exists, say that. | No examples or **Approve** for an unsupported proposal. After the person agrees to a narrower request, show only what the agreed alternative actually does. |

**One way to read examples.** Lead with a concrete situation and result, in task language: **“If Leo's review is still open, Launch brief would stay open.”** Show one or two useful examples near the proposal. Put the rest behind **See examples**. A multi-event example reads as a short sequence of task changes, not a graph. Label each preview locally, including task-shaped results: **Example task · Not saved**. Readers must not mistake an example for a change to their project.

**Inside See examples.** Give each additional example a short situation heading followed by the outcome and why. Don't repeat the examples already shown or state the same outcome twice when it matches. Keep **Expected / In the example** when the result differs or can't be confirmed. For connected steps, keep the same task name and show what changes in the alternate path. Check the expanded view on mobile as well as desktop.

Keep **not supported**, **different from expected**, and **couldn't check** distinct. A mismatch says what the draft would do in the example and what needs fixing. An unavailable check says there is no example result, not that a real write may be pending. Neither can be approved. That is separate from unconfirmed work in live Tasks, where a real write may already have happened. If the saved draft changes, don't present its old results as current. The design sheet is illustrative; in the product, only show a checked result after running the saved draft in isolation.

## In Scope

- **One experience, scoped capabilities.** Personal owners manage their own behavior; current Team admins manage shared behavior. Team membership adds people and shared actions where supported, not an extra authoring mode. Existing saved Personal customizations and drafts stay intact.
- **One versioned capability.** Daymark manages the exact Keir programs, event bindings, and configuration as one immutable revision. One proposal and review cover the whole revision. Explicit approval binds the revision and simulation evidence; activation is a separate decision that switches the selection atomically.
- **Keep started work on its policy.** Capture the active revision when work starts, in the same native transaction that admits it. Later events use that pinned revision, even after a new activation. The new revision applies to new work only. A pin preserves policy, not permission: current authority and revocation still apply.
- **Keep authority and failure handling native.** Daymark enforces membership and admin permissions. Policy effects run under explicit, narrowly scoped authority, not borrowed admin rights. An unavailable gate blocks covered completion. The app rechecks the facts behind an allow decision, the pinned version, and current authority at native commit. Failed or uncertain creation of a required review task leaves a visible, recoverable condition. Reconcile uncertain effects before any repair; never blindly retry or silently bypass the gate.

## Out of Scope

- Custom screens or generated UI in the initial demo. Later, Daymark could supply approved React building blocks and let AI compose them declaratively with an existing tool such as `json-render`. That is a separate presentation layer, not a Keir Core responsibility. No arbitrary frontend code or generic UI framework.
- A hardcoded review product, generic data-model framework, broad team/workspace hierarchy, waiting workflow engine, scheduler, or multi-write Keir invocation. Keir Core stays unchanged unless the proof exposes a concrete, unavoidable limitation.

## Done When

- [ ] People use the same Studio in Personal and Team. In either scope, the agent can compose supported behavior at request time, including dependencies across events, without choosing a preset. It explains unsupported parts before proposing a narrower version. No request-specific host code is needed for behavior the catalog can express.
- [ ] Team offers the common Personal automation capabilities for authorized shared work and adds collaboration. A catalog comparison and real task tests cover parity, including a same-project follow-up with an exact tag, composed title and due date in each scope. A separate request combines a common action with assignment or a review gate. These requests verify the contract; they do not define its shape or its limits.
- [ ] The person reviewing can tell what will happen, what is active, and which work keeps an earlier rule. The shown examples reflect the saved executable revision, and an unmet expectation prevents approval.
- [ ] Members can see the result or the next action in normal tasks. Existing Personal projects and drafts are unchanged. Team access, pinned versions, and native commit checks still hold.
- [ ] Before release, provide the isolated walkthrough and preserve saved data across upgrade, restart, and rollback. Finish audited repair only for a confirmed, fenced no-write. Do not count the scripted demo as live authoring or release approval.

Automatic task creation starts no new workflow. A later human completion of a generated Personal task can run the current standalone completion rule.

The [original Daymark Team Processes draft](../../docs/internal/design-baseline/public/keir_daymark_team_process_feature_spec.md) is preserved unchanged. **What changed after the draft:**

- The review rule is a completion gate, not formal sign-off. It relies on immutable host provenance for the exact linked task, not a name or tag. Rules never wait or recursively admit another creation event.
- The fixture's intake rule changed the triggering task. That native write is not part of the first authoring increment. If added later, it must not overwrite a later human edit.
- Recovery uses the original operation key and never reruns the rule to resolve uncertainty. The [Daymark implementation guide](https://github.com/rore/keir-demo-app/blob/main/docs/native-task-app-design.md) describes the authority and recovery boundaries.
